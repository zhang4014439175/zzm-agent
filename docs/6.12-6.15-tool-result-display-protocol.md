# 6.12-6.15 工具结果、进度事件与展示协议

这项工作是为了解决“同一个工具输出被同时拿去喂模型、展示给用户、保存完整日志、驱动进度 UI”的混用问题。以前工具执行结束后主要得到一个字符串，这个字符串既作为 tool message 回填给模型，又作为终端展示内容，还被事件日志截取预览。短结果还能凑合，一旦遇到测试日志、搜索结果、文件读取、Shell 输出或未来后台任务，就会出现几个真实问题：模型上下文被长输出撑爆，终端只显示一坨难读文本，完整结果没有统一 Artifact 引用，UI 也不知道该实时显示、折叠显示还是只显示摘要。

6.12-6.15 合并开发，是因为这几件事本质上属于同一条链路：`ToolResult` 定义工具结果里哪些内容给模型、哪些内容给界面、哪些内容进 Artifact；`ToolProgressEvent` 定义工具运行中如何连续报告进度；`ToolRenderer` 和 `RendererRegistry` 定义不同工具如何被选择渲染；`DisplayMode` 定义结果默认是内联、折叠、流式、仅摘要还是隐藏。它们一起把“事实记录、模型输入、用户展示、完整产物”拆开，后续 FileReadRenderer、ShellRenderer、后台任务和桌面端都可以复用这套协议。

## 使用场景和例子

### 场景一：测试日志很长，但模型只需要可处理内容，用户需要可读摘要

用户让 Agent 运行测试，工具返回几千行 stdout/stderr。运行时可以创建一个 `ToolResult`：

```python
result = ToolResult.from_text(
    tool_call_id="call-1",
    tool_name="run_shell",
    status="success",
    content=full_pytest_output,
    policy=DisplayPolicy(max_preview_chars=4000, max_preview_lines=80),
    artifacts=[artifact.to_record()],
    metadata={"exit_code": 1, "duration_ms": 1200},
)
```

这里的行为分层是：

- `model_content`：回填给模型的内容，保持 OpenAI tool message 协议可用；
- `display_content`：终端或桌面端看到的预览、截断状态、隐藏行数和隐藏字符数；
- `artifacts`：完整日志或报告的引用；
- `metadata`：退出码、耗时、路径、命中数等机器可读事实；
- `display_mode`：结果较长时自动从 `INLINE` 转为 `COLLAPSED`。

这样模型协议、UI 展示和完整日志不再抢同一个字符串。

### 场景二：Shell 或后台任务运行中需要实时进度

长时间 Shell 命令不能等结束后才告诉用户“完成了”。运行时可以使用 `ToolProgressEmitter` 产生有序的 `ToolProgressEvent`：

```python
emitter = ToolProgressEmitter(conversation.events)
emitter.emit(tool_call_id="call-1", message="starting")
emitter.emit(tool_call_id="call-1", percent=50, stdout_chunk="collected 120 items")
emitter.emit(tool_call_id="call-1", percent=100, message="done")
```

每个 tool call 内的 `sequence` 单调递增，事件同时发布到 `EventBus` 的 `tool.progress`。CLI、日志器或未来桌面端只订阅事件来刷新界面；它们抛错不会中断工具执行。`ToolProgressEmitter` 还保留受限制的最近事件缓冲，避免慢消费者无限积压输出。

### 场景三：不同工具需要不同展示方式

搜索工具适合按文件分组，文件读取适合显示路径和行号，Shell 适合显示命令、stdout/stderr 和退出码。6.12-6.15 先提供选择协议：

```python
registry = RendererRegistry()
registry.register_tool("read_file", file_renderer)
registry.register_category("search", search_renderer)
registry.register_source("mcp", mcp_renderer)

renderer = registry.select(
    ToolRenderContext(
        tool_name="read_file",
        tool_call_id="call-1",
        category="file",
        source="local",
    )
)
```

选择顺序是：具体工具名优先，其次工具类别，再次工具来源，最后使用 `PlainTextToolRenderer` 纯文本降级。Renderer 只能消费 `ToolResult`、`ToolProgressEvent` 和上下文，不允许执行工具或修改核心状态。

## 执行链路

以下链路以一次工具调用为例：

1. 模型请求工具后，`AgentLoop` 按原有逻辑解析工具名和参数，完成权限、Hook、取消检查。
2. 工具执行结束后，原始结果先保存在 `result_str`，兼容旧的工具返回路径。
3. `AgentLoop` 调用 `ToolResult.from_text(...)` 创建结构化结果，写入工具名、tool call id、状态、风险等级和 retryable 信息。
4. `ToolResult.model_content` 通过 `to_model_message()` 回填给模型，保证 assistant tool call 与 tool result 仍然一一配对。
5. `ToolResult.display_content` 保存预览和截断信息，供 CLI、桌面端或测试读取。
6. `TurnState.tool_results` 保存结构化记录，`AgentLoop.last_tool_results` 保存最近一次运行的对象引用，便于回放和验收。
7. 如果工具运行中要汇报进度，调用 `ToolProgressEmitter.emit(...)` 生成 `ToolProgressEvent`，并发布为 `tool.progress` 事件。
8. 展示层通过 `RendererRegistry.select(...)` 找到 Renderer，Renderer 消费上下文、进度事件和 ToolResult，输出 `RenderedToolView`。

## 已知边界

- 当前阶段定义通用协议和默认纯文本渲染，不实现 FileRead、FileEdit、Search、Shell 的专属 Renderer；这些在 P2 的 7.7-7.10 中落地。
- 当前 `ToolResult.model_content` 仍保留完整工具输出，真正的超长工具结果注入预算和自动 Artifact 化属于 7.6。
- 当前 `ToolProgressEmitter` 是同步进程内事件发射器，异步工具、后台任务和流式 Shell 输出会在 P6 扩展。
