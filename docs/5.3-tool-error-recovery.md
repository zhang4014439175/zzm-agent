# 5.3 工具错误恢复增强说明

本文档记录 5.3「工具错误恢复增强」做了什么，并明确每个功能点对应到哪里的代码。读这个文档时，可以先看“执行链路总览”，再按功能点跳到对应文件。

## 执行链路总览

5.3 的核心链路是：

```text
AgentLoop._execute_tool_with_retries()
→ registry.call(name, args)
→ 工具抛出异常
→ tool_error_from_exception(exc)
→ ToolError
→ 判断 retryable / deterministic / retry_after_seconds
→ 必要时 sleep 后重试
→ 最终把 ToolError.to_json() 作为 tool Observation 返回给模型
```

对应代码：

- `zzm_agent/core/agent_loop.py`
  - `AgentLoop.__init__()`：新增重试配置参数；
  - `AgentLoop._execute_tool_with_retries()`：执行工具、捕获异常、决定是否重试；
  - `AgentLoop._retry_delay_for_error()`：计算 Retry-After 或指数退避等待时间；
  - `AgentLoop._format_retried_error()`：把最终错误整理成模型可读 JSON。
- `zzm_agent/core/errors.py`
  - `ToolError`：结构化错误对象；
  - `tool_error_from_exception()`：异常到错误分类的转换入口；
  - `_extract_retry_after_seconds()`：从异常或响应头提取 Retry-After；
  - `_coerce_retry_after()`：把 Retry-After 的数字或日期格式转成秒数。
- `tests/test_tool_error_recovery.py`
  - 5.3 专项测试。
- `docs/roadmap.md`
  - 5.3 勾选完成，下一任务推进到 5.4。

## 1. ToolError 错误结构扩展

对应代码：

- `zzm_agent/core/errors.py`
  - `class ToolError`
  - `ToolError.to_json()`
  - `ToolError.retry_summary()`

这个功能做什么：

`ToolError` 是工具执行失败后返回给模型的结构化 Observation。5.3 之前，它主要只有：

- `error_type`
- `message`
- `recovery_hint`
- `retryable`

5.3 新增了：

- `category`：错误分类；
- `deterministic`：是否确定性失败；
- `attempts`：尝试次数；
- `retry_after_seconds`：外部服务建议等待多久再重试。

为什么要改这里：

AgentLoop 需要根据错误信息做自动决策。如果错误对象只有一个 `retryable: true/false`，判断太粗糙。现在 `ToolError` 同时告诉框架：

- 这是什么类型的失败；
- 重复同样调用有没有意义；
- 已经尝试了几次；
- 是否应该等一段时间再试。

代码上怎么串起来：

```text
工具异常
→ tool_error_from_exception(exc)
→ 返回 ToolError(...)
→ AgentLoop 根据 ToolError.retryable 判断是否自动重试
→ 最终 ToolError.to_json() 写入 role: "tool" 消息
```

## 2. 错误分类常量

对应代码：

- `zzm_agent/core/errors.py`
  - `ERROR_ARGUMENT`
  - `ERROR_PERMISSION`
  - `ERROR_TIMEOUT`
  - `ERROR_ENVIRONMENT`
  - `ERROR_EXTERNAL_SERVICE`
  - `ERROR_BUSINESS`
  - `ERROR_UNKNOWN`

这个功能做什么：

这些常量定义了工具错误的标准分类，避免各处手写字符串导致不一致。

当前分类含义：

- `argument`：参数错误，例如 JSON 非法、缺少参数、参数类型不对、工具不存在；
- `permission`：权限错误；
- `timeout`：超时错误；
- `environment`：本地环境错误，例如文件不存在、路径或系统状态异常；
- `external_service`：外部服务错误，例如连接失败、限流；
- `business`：工具业务逻辑错误；
- `unknown`：兜底未知错误。

为什么要改这里：

后续 P1/P2/P6 会继续扩展权限状态、工具生命周期、Circuit Breaker。错误分类是这些能力的底座。比如：

- `permission` 以后可以接 PermissionState；
- `external_service` 以后可以接 Circuit Breaker；
- `argument` 可以接参数校验和模型纠错；
- `environment` 可以接文件状态缓存和恢复提示。

## 3. 异常到 ToolError 的转换

对应代码：

- `zzm_agent/core/errors.py`
  - `tool_error_from_exception(exc: Exception) -> ToolError`

这个功能做什么：

`tool_error_from_exception()` 是 5.3 的错误分类入口。任何工具执行异常都会先进入这里，再被转换成结构化 `ToolError`。

当前映射关系：

```text
TimeoutError        → CommandTimeoutError / timeout / retryable=True / deterministic=False
JSONDecodeError     → InvalidToolArguments / argument / retryable=False / deterministic=True
KeyError            → ToolNotFound / argument / retryable=False / deterministic=True
PermissionError     → ToolPermissionError / permission / retryable=False / deterministic=True
FileNotFoundError   → FileNotFoundError / environment / retryable=False / deterministic=True
TypeError           → ToolArgumentError / argument / retryable=False / deterministic=True
ConnectionError     → external_service / retryable=True / deterministic=False
OSError             → environment / retryable=False / deterministic=True
其他 Exception      → business / retryable=False / deterministic=True
```

为什么要改这里：

以前 `TypeError` 是 `retryable=True`，这其实不合理。比如工具缺少必填参数，重复调用同样参数不会突然成功。5.3 把这类确定性错误改成不自动重试，让模型拿到错误后改参数或换工具。

代码上怎么串起来：

```text
AgentLoop._execute_tool_with_retries()
except Exception as exc:
    last_error = tool_error_from_exception(exc)
```

也就是说，AgentLoop 本身不直接判断每一种 Python 异常，而是把分类职责交给 `errors.py`。

## 4. CommandTimeoutError 超时错误

对应代码：

- `zzm_agent/core/errors.py`
  - `class CommandTimeoutError(ToolError)`

这个功能做什么：

`CommandTimeoutError` 是超时错误的专用结构化错误。它会设置：

- `error_type="CommandTimeoutError"`
- `category="timeout"`
- `retryable=True`
- `deterministic=False`

为什么要这样做：

超时通常不是确定性失败。可能只是外部环境慢、命令偶发卡顿、任务范围稍大。所以它允许底层有界重试。

对 ReAct 的影响：

如果工具第一次超时，AgentLoop 可以先自动重试一次，而不是马上把错误交还给模型。但达到 `max_tool_retries` 后，仍会停止自动重试，把错误反馈给模型。

## 5. 确定性错误禁止自动重试

对应代码：

- `zzm_agent/core/errors.py`
  - `tool_error_from_exception()`
- `zzm_agent/core/agent_loop.py`
  - `AgentLoop._execute_tool_with_retries()`

这个功能做什么：

确定性错误会被设置为：

```text
retryable=False
deterministic=True
```

AgentLoop 看到 `retryable=False` 后，会直接返回错误，不会继续自动调用同一个工具。

典型确定性错误：

- 参数缺失；
- 参数类型错误；
- 工具名不存在；
- 文件不存在；
- 权限不足；
- 本地环境明确不满足。

代码上怎么生效：

`AgentLoop._execute_tool_with_retries()` 中有这个判断：

```text
if not last_error.retryable or attempts >= max_attempts:
    return _ToolExecutionOutcome(...)
```

所以只要 `tool_error_from_exception()` 把某个错误标记为 `retryable=False`，自动重试就会停止。

为什么重要：

这避免了 Agent 做无意义的重复调用。比如少传了参数，重复调用 10 次也还是少传参数。正确行为是把错误交给模型，让模型修改参数。

## 6. 可重试错误的有界自动重试

对应代码：

- `zzm_agent/core/agent_loop.py`
  - `AgentLoop.__init__()`
  - `AgentLoop._execute_tool_with_retries()`

这个功能做什么：

AgentLoop 对 `retryable=True` 的错误进行有限次数自动重试。次数由 `max_tool_retries` 控制。

相关参数：

- `max_tool_retries`：最多自动重试几次；
- `retry_base_delay`：第一次重试前的基础等待时间；
- `retry_max_delay`：最大等待时间；
- `retry_sleep`：实际等待函数。

执行逻辑：

```text
attempts = 0
max_attempts = max_tool_retries + 1

while attempts < max_attempts:
    尝试调用工具
    如果成功：返回成功
    如果失败：转换为 ToolError
    如果不可重试或达到上限：返回错误
    否则：计算 delay，sleep，然后继续
```

为什么要这样做：

有些错误是临时性的，比如超时或外部服务连接失败。底层自动重试可以提升成功率。但重试必须有上限，否则会重新变成死循环。

## 7. Retry-After 支持

对应代码：

- `zzm_agent/core/errors.py`
  - `_extract_retry_after_seconds()`
  - `_coerce_retry_after()`
- `zzm_agent/core/agent_loop.py`
  - `AgentLoop._retry_delay_for_error()`

这个功能做什么：

当外部服务告诉我们“多久以后再试”，AgentLoop 会优先使用这个等待时间。

支持来源：

- 异常对象上的 `retry_after_seconds`；
- 异常对象上的 `retry_after`；
- HTTP 响应对象 headers 里的 `Retry-After` 或 `retry-after`。

支持格式：

- 秒数，例如 `2`、`2.0`、`"2"`；
- HTTP 日期格式。

代码上怎么串起来：

```text
ConnectionError
→ tool_error_from_exception()
→ _extract_retry_after_seconds(exc)
→ ToolError(retry_after_seconds=...)
→ AgentLoop._retry_delay_for_error()
→ 优先使用 retry_after_seconds
```

为什么重要：

外部服务限流时，如果服务明确要求 2 秒后再试，Agent 不应该 0.25 秒后就继续撞上去。遵守 Retry-After 更稳定，也更符合生产系统的重试礼仪。

## 8. 指数退避重试

对应代码：

- `zzm_agent/core/agent_loop.py`
  - `AgentLoop._retry_delay_for_error()`

这个功能做什么：

如果错误没有提供 Retry-After，就使用指数退避计算下一次重试前等待多久。

公式：

```text
delay = retry_base_delay * (2 ** retry_index)
delay = min(delay, retry_max_delay)
```

示例：

```text
retry_base_delay = 0.5
retry_max_delay = 5.0

第一次重试前等待 0.5 秒
第二次重试前等待 1.0 秒
第三次重试前等待 2.0 秒
最多不超过 5.0 秒
```

为什么要这样做：

指数退避可以降低对不稳定依赖的压力，避免工具在短时间内疯狂重试。

## 9. retry_sleep 注入

对应代码：

- `zzm_agent/core/agent_loop.py`
  - `AgentLoop.__init__()`
  - `self.retry_sleep = retry_sleep or sleep`
- `tests/test_tool_error_recovery.py`
  - `_loop(..., sleeps=sleeps)`

这个功能做什么：

`retry_sleep` 是等待函数注入点。生产环境不传时，默认使用 `time.sleep`；测试时可以传入 `list.append` 之类的函数来记录等待时间。

测试中的用法：

```text
sleeps = []
retry_sleep=sleeps.append
```

这样测试可以断言：

```text
sleeps == [0.5, 1.0]
```

为什么要这样做：

如果测试真的 sleep，会变慢。通过注入 `retry_sleep`，测试既能验证退避策略，又不需要真实等待。

## 10. 最终错误恢复摘要

对应代码：

- `zzm_agent/core/errors.py`
  - `ToolError.retry_summary()`
- `zzm_agent/core/agent_loop.py`
  - `AgentLoop._format_retried_error()`

这个功能做什么：

当工具最终失败时，AgentLoop 会把错误整理成更完整的 JSON，再作为 tool message 返回给模型。

最终 JSON 包含：

- `error_type`
- `message`
- `recovery_hint`
- `retryable`
- `category`
- `deterministic`
- `attempts`
- `retry_after_seconds`

`_format_retried_error()` 还会把自动重试耗尽的信息追加到 `recovery_hint` 中，例如：

```text
Automatic retry exhausted after 1 retry attempt(s).
```

为什么要这样做：

模型拿到的是 Observation。如果 Observation 足够结构化，模型更容易做正确下一步：

- 参数错了：改参数；
- 权限错了：请求用户授权或换方案；
- 文件不存在：先搜索文件；
- 外部服务失败：报告阻塞或稍后重试；
- 超时：缩小范围或换后台命令。

## 11. 5.3 专项测试

对应代码：

- `tests/test_tool_error_recovery.py`
  - `FakeStore`
  - `_tool_call()`
  - `_loop()`
  - `test_deterministic_argument_error_is_not_automatically_retried()`
  - `test_retryable_timeout_uses_exponential_backoff_before_success()`
  - `test_external_service_error_respects_retry_after_and_reports_recovery_summary()`

这个功能做什么：

新增测试固定 5.3 的核心行为。

测试 1：确定性参数错误不自动重试

- 对应函数：`test_deterministic_argument_error_is_not_automatically_retried()`
- 覆盖行为：
  - 缺少必填参数；
  - 工具函数本体不会被调用成功；
  - 错误 JSON 中 `category="argument"`；
  - `deterministic=True`；
  - `retryable=False`；
  - `attempts=1`。

测试 2：超时错误使用指数退避

- 对应函数：`test_retryable_timeout_uses_exponential_backoff_before_success()`
- 覆盖行为：
  - 前两次抛 `TimeoutError`；
  - 第三次成功；
  - `sleeps == [0.5, 1.0]`；
  - 最终 tool Observation 是成功结果。

测试 3：外部服务错误遵守 Retry-After

- 对应函数：`test_external_service_error_respects_retry_after_and_reports_recovery_summary()`
- 覆盖行为：
  - `ConnectionError` 带 `retry_after_seconds=2.0`；
  - AgentLoop 重试前等待 `2.0`；
  - 重试耗尽后返回结构化错误；
  - 错误 JSON 中包含 `category="external_service"`、`attempts=2` 和恢复摘要。

为什么测试里有 FakeStore：

`AgentLoop.run()` 需要 `store` 提供：

- `load_history()`
- `build_turn_messages()`
- `append()`
- `save_latest_context()`

5.3 测的是工具错误恢复，不是 MemoryStore 文件读写。为了避免 Windows 文件权限影响测试，专项测试使用内存版 `FakeStore`，让测试聚焦在 AgentLoop 的错误恢复逻辑。
