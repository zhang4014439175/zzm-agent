# 6.17-6.20 QueryEngine、ModelAdapter、StreamEvent 与 CLI 主链路迁移

## 使用场景

本阶段解决 CLI、模型 provider、流式输出和会话状态耦合在一起的问题。后续终端版、桌面版、后台任务和多 Agent 都应该通过同一条会话入口提交消息，而不是各自直接拼装 `AgentLoop`、OpenAI SDK 响应、流式 chunk 和状态快照。

一句话说：**用户只是在终端里输入一句话，但系统内部要同时处理模型请求、流式展示、工具调用、状态保存、会话恢复和未来桌面端 UI。QueryEngine、ModelAdapter、ModelStreamEvent 就是把这些事情拆清楚。**

典型场景：

- CLI 用户发送一条消息，运行时通过 `QueryEngine.submit_message()` 创建 Turn、调用 AgentLoop、保存会话快照并返回最终结果；
- provider 流式返回正文、reasoning、tool call delta 或 usage 时，先被 `ModelAdapter` 规范化，再转成 `ModelStreamEvent`；
- CLI 只渲染 `content_delta`，不会把 reasoning、status、tool call 参数或最终事件混在正文里；
- 伪 XML 文本工具调用仍走兼容解析路径，不会被当成用户可见正文渲染；
- 6.16 的 `StateSnapshotStore` 现在由 QueryEngine 在 Turn 开始、完成和失败边界调用。

## 先看一个完整例子

假设用户在 CLI 输入：

```text
帮我看一下为什么测试失败，并修复。
```

旧链路里，CLI 可能直接调用：

```text
loop.run(user_input, stream=True, on_text_chunk=...)
```

这样的问题是：

- CLI 只知道“有一段文字流出来了”，不知道这是正文、推理摘要、工具调用参数还是最终答案；
- OpenAI、OpenRouter、Anthropic、本地模型返回的 chunk 结构可能不同，AgentLoop 和 CLI 容易到处写 provider 兼容逻辑；
- Turn 开始、失败、完成时是否保存状态快照，没有一个统一入口负责；
- 未来桌面端如果也直接调 AgentLoop，就会复制一套会话、取消、权限和状态逻辑。

新链路改成：

```python
result = query_engine.submit_message(
    "帮我看一下为什么测试失败，并修复。",
    stream=True,
    on_stream_event=handle_event,
)
```

这时内部发生的事情是：

```text
1. QueryEngine 创建 TurnState
2. QueryEngine 保存 turn.started 快照
3. QueryEngine 调用 AgentLoop.run()
4. AgentLoop 调用模型
5. ModelAdapter 把 provider 原始响应转成统一结构
6. AgentLoop 发出 ModelStreamEvent
7. CLI 只渲染 content_delta
8. AgentLoop 执行工具、提交消息、得到最终回答
9. QueryEngine 保存 turn.completed 快照
10. QueryEngine 返回 QueryResult.reply
```

## 三个概念分别干什么

### QueryEngine：统一入口

QueryEngine 解决的是“谁负责一轮用户消息”的问题。

它负责：

- 接收用户输入；
- 创建和保存 Turn 状态；
- 调用 AgentLoop；
- 收集流事件；
- 在 Turn 开始、失败、完成时保存快照；
- 返回最终结果。

例子：

```python
from zzm_agent.core.query_engine import QueryEngine

engine = QueryEngine.with_snapshot_path(
    agent_loop=loop,
    snapshot_path=".zzm_agent/state/session-1.json",
)

result = engine.submit_message("运行测试并修复失败", stream=True)

print(result.reply)
print(result.turn.final_response)
```

这里的重点不是“多包了一层函数”，而是以后 CLI、桌面端、后台任务、多 Agent 都走这个入口。这样恢复、取消、权限、Usage、Artifact、事件订阅不会分裂成多套实现。

### ModelAdapter：隔离模型供应商差异

ModelAdapter 解决的是“不同模型 SDK 返回结构不同”的问题。

比如 OpenAI-compatible 的非流式响应可能长这样：

```python
response.choices[0].message.content
response.choices[0].message.tool_calls
response.usage
```

某些 provider 的 streamed chunk 可能是：

```python
chunk.choices[0].delta.content
chunk.choices[0].delta.tool_calls
chunk.usage
```

AgentLoop 不应该到处知道这些 SDK 字段。现在统一交给：

```python
adapter = OpenAIChatCompletionsAdapter(client)
normalized = adapter.normalize_response(response)

normalized.content
normalized.tool_calls
normalized.raw_usage
```

streaming 也统一成：

```python
for chunk in adapter.iter_stream_chunks(response):
    chunk.content_delta
    chunk.reasoning_summary
    chunk.tool_call_deltas
    chunk.raw_usage
```

这样以后换 provider 时，优先改 adapter，不让 CLI、QueryEngine、桌面 UI 一起跟着改。

### ModelStreamEvent：区分“正在想”和“最终回答”

ModelStreamEvent 解决的是“流式输出混在一起”的问题。

以前终端可能只收到这种字符串：

```text
我需要先检查测试。<tool_call>run_shell...
```

CLI 很难判断哪些该展示、哪些该隐藏、哪些应该放到工具面板。

现在改成事件：

```python
ModelStreamEvent.status("turn.started")
ModelStreamEvent.reasoning_summary("需要先运行测试定位失败。")
ModelStreamEvent.content_delta("我先运行测试。")
ModelStreamEvent.tool_call_delta(tool_name="run_shell", arguments_delta="pytest")
ModelStreamEvent.content_delta("失败原因是...")
ModelStreamEvent.final_message("已修复，测试通过。")
```

CLI 当前只渲染：

```python
if event.kind is ModelStreamEventKind.CONTENT_DELTA:
    render_markdown(event.text)
```

未来桌面端可以这样分区展示：

```text
状态栏：status
思考/摘要面板：reasoning_summary
对话正文：content_delta / final_message
工具面板：tool_call_delta / tool_result
用量面板：usage
错误面板：error
```

## 新增模块

### `zzm_agent.core.model_adapter`

提供 OpenAI-compatible provider 的适配层：

- `ModelCapabilities`：声明模型能力；
- `ModelRequest`：标准请求结构；
- `ModelResponse`：标准非流式响应；
- `ModelStreamChunk`：标准流式 chunk；
- `OpenAIChatCompletionsAdapter`：屏蔽 SDK response、message、delta 和 tool call 字段差异。

### `zzm_agent.core.model_stream`

提供用户可见流事件协议：

- `status`
- `reasoning_summary`
- `content_delta`
- `tool_call_delta`
- `tool_result`
- `usage`
- `final_message`
- `error`

这些事件用于区分运行状态、推理摘要、正文、工具调用、最终回答和错误，避免 CLI 或桌面端再解析混杂字符串。

事件记录例子：

```json
{
  "kind": "content_delta",
  "text": "我先运行测试。",
  "tool_call_id": null,
  "tool_name": null,
  "arguments_delta": "",
  "usage": {},
  "metadata": {}
}
```

工具调用增量例子：

```json
{
  "kind": "tool_call_delta",
  "text": "",
  "tool_call_id": "call_1",
  "tool_name": "run_shell",
  "arguments_delta": "{\"command\":\"pytest tests/test_cli.py -q\"}",
  "usage": {},
  "metadata": {
    "index": 0
  }
}
```

### `zzm_agent.core.query_engine`

提供跨 Turn 会话入口：

- `QueryEngine.submit_message()`：统一提交用户消息；
- `QueryResult`：返回最终回复、事件列表和 TurnState；
- Turn 边界自动保存 `ConversationState` 快照；
- 保留 `AgentLoop.run()` 兼容路径，AgentLoop 仍负责单 Turn 内部 ReAct。

## 执行链路

```text
CLI 输入
→ QueryEngine.submit_message()
→ 保存 turn.started 快照
→ AgentLoop.run()
→ ModelAdapter 规范化 provider 响应
→ ModelStreamEvent 分层发出流式事件
→ CLI 渲染 content_delta
→ AgentLoop 完成 ReAct 与消息提交
→ QueryEngine 保存 turn.completed / turn.failed 快照
→ 返回 QueryResult.reply
```

对应到一次真实运行，可以理解成下面这条事件序列：

```text
用户输入：
  帮我看一下为什么测试失败，并修复。

QueryEngine:
  status: turn.started
  snapshot: .zzm_agent/state/<session>.json

ModelAdapter:
  把 provider streamed chunk 转成 ModelStreamChunk

AgentLoop:
  reasoning_summary: 需要先运行测试定位失败
  content_delta: 我先运行测试。
  tool_call_delta: run_shell {"command":"pytest tests/test_cli.py -q"}

ToolRegistry:
  执行 run_shell
  返回测试失败日志

AgentLoop:
  content_delta: 失败来自 test_cli.py 的断言...
  final_message: 已修复，相关测试通过。

QueryEngine:
  snapshot: turn.completed
  result.reply: 已修复，相关测试通过。
```

这就是“发布事件 / 接收事件”的含义：AgentLoop 在执行过程中发布 `ModelStreamEvent`，CLI 或桌面端订阅这些事件并决定怎么展示。

当前 CLI 的接收逻辑很简单：

```python
def on_stream_event(event):
    if event.kind is ModelStreamEventKind.CONTENT_DELTA:
        stream_renderer.push(event.text)
```

也就是说，CLI 现在只把正文放到对话流里。`reasoning_summary`、`tool_call_delta`、`status` 等事件已经进入链路，但不会混进最终回答。后续 P2/P9 可以把这些事件做成更丰富的状态栏、工具面板和桌面视图。

## 兼容策略

- `AgentLoop.run(user_input, stream=True, on_text_chunk=...)` 继续可用；
- 新增 `on_stream_event`，用于 CLI 和未来桌面端消费分层事件；
- CLI 优先走 `QueryEngine`，如果运行时没有 QueryEngine，仍降级到旧 `loop.run()`；
- Slash Command 仍复用原有 runtime 对象，模型切换等命令继续修改同一个 AgentLoop。

## 为什么现在还保留 `loop.run()`

这是为了避免一次迁移把所有旧测试、Slash Command 和 REPL 行为打断。

当前关系是：

```text
CLI
└── QueryEngine.submit_message()
    └── AgentLoop.run()
        ├── ModelAdapter
        ├── ToolRegistry
        ├── MemoryStore
        └── HookRegistry
```

后续会逐步把更多跨 Turn 行为移动到 QueryEngine，但 AgentLoop 仍然保留为“单个 Turn 内部的 ReAct 执行器”。
