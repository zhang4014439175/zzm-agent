# 8.9 WorkspaceRuntime 与 EffectRecord

## 一句话说明

以前文件修改、Shell 命令和 Git 暂存分别执行、分别记录，系统无法用同一种方式回答“刚才改了什么、是否得到允许、能不能撤销”。现在这三类操作都会经过统一的工作区执行边界，并留下副作用记录。用户仍然使用原来的文件工具、Shell 工具和 Git 命令，但文件及 Git 操作有了统一的检查和撤销依据。

## 为什么需要它

编码 Agent 不只是读取信息，还会改变真实工作区。写文件、运行命令和修改 Git 暂存区都可能影响用户正在进行的工作。

开发前，文件工具有一套路径保护和 ChangeSet 记录，Shell 直接启动进程，GitWorkflow 又单独保存最近一次反向命令。三者没有共同的事实格式。因此，后续的事件日志、任务恢复或其他界面无法可靠地用同一种方式展示这些操作。

本次增加的 WorkspaceRuntime，可以理解为“所有工作区改动都要经过的登记台”。EffectRecord 是“副作用记录”，也就是一次真实操作的收据。它会记录操作类型、目标、是否授权、执行结果、检查点和撤销状态。

## 一个实际使用例子

用户让 Agent 把 `config.yaml` 中的超时时间从 30 秒改成 60 秒。

1. Agent 调用文件编辑工具，并请求修改 `config.yaml`。
2. 原有路径沙箱先确认文件位于允许的工作区内。需要用户确认时，仍按原权限流程询问。
3. 工作区执行边界收到这次操作，记录它是一次文件编辑，并保存修改前的文件内容作为检查点。检查点就是“出问题时可以回到的旧版本”。
4. 文件工具把 30 改为 60。执行成功后，副作用记录变为 `applied`，表示操作已经生效，同时保存修改后的内容摘要。
5. 用户随后执行撤销。系统先比较当前文件是否仍等于 Agent 修改后的版本。
6. 如果文件没有被其他人继续修改，系统恢复修改前的内容，并把记录标为 `reverted`。
7. 如果用户已经手动把超时时间改成 90，系统不会用旧内容覆盖它，而是报告冲突并保留用户当前文件。

用户看到的文件工具成功信息和原来一致。变化主要体现在系统现在有可靠的操作记录，并且撤销时会保护后续编辑。

## 功能的大致流程

1. 用户或 Agent 发起文件、Shell 或 Git 操作。
2. 原有工具权限与工作区路径规则先判断操作是否允许。
3. 统一工作区边界再次接收授权结果，并创建一条待执行记录。被拒绝的操作不会运行，但会留下拒绝事实。
4. 对文件和 Git 这类可逆操作，系统在执行前准备恢复信息。Shell 命令通常无法安全地自动反向执行，因此只记录事实，不声称可以撤销。
5. 系统调用原来的文件、进程或 Git 实现。公开命令和返回文本保持不变。
6. 成功时记录变为已应用；异常时记录失败原因。
7. 用户请求撤销时，系统寻找指定记录或最近一条可逆记录。
8. 文件撤销前会检查当前内容，防止覆盖用户或其他工具的后续修改。Git 撤销执行与原操作对应的反向暂存命令。
9. 撤销成功、失败或冲突都会更新同一条记录，供后续日志和恢复功能读取。

## 开发前和开发后的区别

开发前：

- 文件、Shell 和 Git 各自执行，没有共同的副作用记录。
- 文件撤销由 ChangeSet 单独观察工具事件，Git 只在内存中保存最近一次反向命令。
- 其他运行入口难以统一查询某次操作是否授权、成功或已撤销。
- Shell 命令与文件、Git 操作没有共同的审计边界。

开发后：

- 三类操作都经过 WorkspaceRuntime，并生成相同格式的 EffectRecord。
- 文件编辑、覆盖和追加会保存修改前后的检查点信息。
- 文件检查点写入 Journal 后，可以由新的 Runtime 实例恢复并撤销。
- 文件发生后续修改时，撤销会明确冲突，不会静默覆盖。
- Git stage 和 unstage 的执行与撤销属于同一条 Effect。
- Shell 命令记录工作目录、命令和执行状态，但不会伪装成可自动撤销操作。

## 现在已经支持的能力

- 统一记录文件、进程和 Git 三类副作用。
- 在动作执行前调用统一授权回调。
- 记录允许、拒绝、执行中、成功、失败、已撤销和冲突状态。
- 为文件修改保存修改前和修改后的内容检查点。
- 撤销文件创建、覆盖、追加和精确编辑产生的变更。
- 在文件已被继续修改时拒绝危险撤销。
- 持久化文件 Effect，并在重新创建 Runtime 后恢复撤销。
- 撤销最近一次 Git stage 或 unstage。
- 保留原 SandboxProfile、工具风险确认、ChangeSet 和 GitWorkflow 公开入口。

## 当前限制（还做不到什么）

- Shell 命令可能在内部修改许多文件或启动外部程序。目前只记录命令执行事实，不分析命令产生的全部系统变化，也不能通用撤销 Shell。
- Git Effect 当前覆盖 stage、unstage 和对应撤销，不包含 commit、branch、merge、rebase 或远程推送。
- 默认由工具创建的 WorkspaceRuntime 使用进程内记录；只有调用方提供 Journal 路径时，Effect 才会跨进程持久化。
- 现有 `/undo` 仍使用 8.4 的 ChangeSetStore。WorkspaceRuntime 已提供底层统一撤销能力，但 CLI 命令尚未切换为跨 File、Shell、Git 的统一撤销列表。
- 当前记录是本地 JSON 数据，不支持多个进程同时写入，也不提供数据库事务。这属于后续可选 SQLite Journal，而不是本任务范围。

## 给开发者看的实现位置

- `zzm_agent/workspace/effects.py`
  - `EffectRecord`：保存一次副作用的类型、目标、授权、状态、检查点、错误和撤销时间。
  - `EffectUndoResult`：返回撤销是否成功及失败原因。
- `zzm_agent/workspace/runtime.py`
  - `WorkspaceRuntime.execute()`：执行统一授权、状态记录和错误记录。
  - `execute_file_mutation()`：保存文件前后快照并注册冲突感知撤销。
  - `undo()`：选择可逆 Effect，执行撤销并更新状态。
- `zzm_agent/workspace/filesystem.py`：把文件变更转交统一 Runtime。
- `zzm_agent/workspace/process.py`：把 Shell/进程执行转交统一 Runtime。
- `zzm_agent/workspace/git.py`：把 Git 索引变更及反向操作转交统一 Runtime。
- `zzm_agent/plugins/file_ops.py`：`file_edit`、`write_file`、`file_append` 保留旧工具协议并接入文件适配器。
- `zzm_agent/plugins/shell.py`：`run_shell` 保留原输出格式并接入进程适配器。
- `zzm_agent/cli_support/git_workflow.py`：stage、unstage 和 undo 共享同一个 Git Effect。

执行链路：

```text
用户或 Agent 发起操作
→ 原有权限与路径规则检查
→ WorkspaceRuntime 创建 EffectRecord 并授权
→ 可逆操作保存检查点
→ 文件、进程或 Git 适配器执行原动作
→ 更新为 applied / failed / denied
→ 用户撤销时检查冲突并执行反向动作
→ 更新为 reverted / conflicted
```

## 测试如何证明它有效

`tests/test_workspace_runtime.py` 覆盖：

- 授权拒绝后动作不会执行，同时会记录 denied Effect。
- 文件修改会创建检查点，并能恢复原内容。
- 用户后续修改文件时，撤销会报告冲突且保留用户内容。
- Journal 持久化后，新 Runtime 实例仍能撤销已记录的文件创建。
- Git stage 会生成可逆 Effect，undo 后同一条记录变为 reverted。

既有测试继续覆盖 File、Shell、GitWorkflow、ChangeSet、工作区沙箱，以及 P2/P3 阶段验收。这证明新边界没有改变原工具签名、成功输出、路径保护和 Git 确认行为。

实际验证结果：

- 副作用相关既有回归：`54 passed, 2 skipped`。
- WorkspaceRuntime 新增测试：`4 passed`。
- 完整回归：`371 passed, 2 skipped`。

这些测试共同证明：三类副作用已经进入统一记录边界；文件和 Git 的可逆操作能够安全撤销；拒绝、失败和冲突不会被误报为成功。
