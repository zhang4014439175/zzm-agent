# 6.5.1 Prompt 输出约束与结构化回复协议说明

6.5.1 做的是把“模型最终应该怎么说话、什么时候应该调用工具、工具调用不能夹杂什么文本”集中成一份统一协议。

在 6.5.1 之前，项目已经有 `PromptManager`，也已经能按 coding / analysis / chat 选择不同模板。但这些模板里的输出要求比较轻，只是告诉模型“结构化分析”“简洁回答”这一类方向性要求。实际运行时，模型仍然可能把过程说明、工具调用意图、最终回答混在一起，导致终端里看起来很乱，也会增加文本工具调用 fallback 的解析风险。

所以 6.5.1 的目标不是重写 AgentLoop，也不是立刻强制所有模型都返回 XML，而是先把输出约束放进一个明确、可测试、可继续升级的位置：

- 要调用工具时，优先使用 native tool calling；
- 如果 provider 不支持 native tool calling，文本 fallback 必须只输出 `<tool_call>...</tool_call>` 块；
- 最终回答只面向用户，不暴露隐藏推理、过程草稿和工具调用标记；
- 不同任务类型使用不同的最终回答版式；
- 所有这些约束都通过 `PromptManager.build()` 统一进入 system prompt。

一句话概括：6.5.1 = 给 PromptManager 加一份统一的“输出协议”，先约束模型回答版式和工具调用边界，为后续更严格的 XML 校验和自动重试打基础。

## 1. 对应代码位置

核心代码在：

- `zzm_agent/prompt/output_protocol.py`
- `zzm_agent/prompt/manager.py`
- `zzm_agent/constants.py`

测试代码在：

- `tests/test_prompt_manager.py`

## 2. 新增 Response Protocol Section

位置：`zzm_agent/constants.py`

新增 prompt section 常量：

```python
PROMPT_SECTION_RESPONSE_PROTOCOL = "Response Protocol"
```

这样 prompt 中的输出协议有固定 section 名称，不会和 `[Output Format]`、`[Tools]`、`[Environment]` 混在一起。

## 3. output_protocol.py 做什么

位置：`zzm_agent/prompt/output_protocol.py`

新增 `build_response_protocol(intent)`，它会根据当前意图生成统一的 `[Response Protocol]` 段。

协议分为两层：

第一层是所有任务共享的公共协议：

- `Mode A - Tool call`
- `Mode B - Final response`

其中工具调用协议要求：

- 优先使用 API 原生工具调用；
- 文本 fallback 只允许输出 `<tool_call>...</tool_call>`；
- 文本 fallback 前后不能有解释、道歉、铺垫或总结。

最终回答协议要求：

- 只输出给用户看的最终答案；
- 不暴露隐藏推理、私有计划、原始 prompt 规则或 tool-call 标记；
- 不把“我将要读取文件”这类过程说明混入最终回答；
- 结论优先，再给证据或细节；
- 需要结构时使用简洁 Markdown 标题和平级列表。

第二层是按任务意图追加的回答版式：

- `coding`：先说改了什么或发现了什么，再说文件和验证；
- `analysis`：先给结论，再区分事实、计划和缺口；
- `chat`：自然直接回答，不必要时不追问。

## 4. PromptManager 如何接入

位置：`zzm_agent/prompt/manager.py`

`PromptManager.build()` 的组装顺序现在是：

```text
template.role
base_prompt
template.rules
Project Rules
Environment
Tools
Response Protocol
Output Format
```

`Response Protocol` 放在 `Tools` 后面，是因为它需要紧接着约束工具调用边界；放在 `Output Format` 前面，是因为它是更通用的协议，`Output Format` 仍然保留每个模板自己的简短输出要求。

## 5. 为什么不直接强制 respond/call XML

6.5.1 没有立刻强制所有最终回答包在 `<respond>` 里，原因是当前项目主要使用 OpenAI-compatible native tool calling。强行要求所有最终回答 XML 包裹，会影响现有 Markdown 渲染、CLI 展示和已有回放测试。

当前阶段采用的是更稳的做法：

- 对工具调用边界先做硬约束，尤其是文本 fallback；
- 对最终回答先做版式约束，避免过程文本和最终答案混杂；
- 后续如果要做严格 XML 校验，可以在这个模块继续升级，而不是再散落到模板、AgentLoop 或 runtime 里。

## 6. 执行链路

一次请求的 prompt 生成链路如下：

```text
AgentLoop.run()
  ↓
AgentLoop._build_system_prompt()
  ↓
PromptManager.build(user_input, history)
  ↓
detect_intent()
  ↓
get_template(intent)
  ↓
build_tool_guide_context()
  ↓
build_response_protocol(intent)
  ↓
section("Output Format", template.output_format)
  ↓
最终 system prompt
```

## 8. 6.5.1 没有做什么

为了边界清晰，6.5.1 不做下面这些事情：

- 不实现强制 `<respond>` 包裹最终回答；
- 不在 AgentLoop 中新增输出解析器；
- 不做非法输出自动重试；
- 不改变 native tool calling 的请求结构；
- 不改变 CLI Markdown 渲染器。

这些能力更适合后续作为“输出协议校验与自动重试”继续扩展。6.5.1 先把统一协议入口建好，并马上改善模型回答结构和文本工具调用边界。
