# 6.4 运行时消息、待提交消息与持久化消息分层说明

## 这项工作整体在做什么

6.4 做的是给 Agent 的消息流建立“账本”。

在 6.4 之前，`AgentLoop.run()` 里主要靠两个普通列表维护消息：

```text
messages       给模型看的当前上下文
turn_messages  本轮结束后准备写入历史的消息
```

这在简单 ReAct 循环里可以工作，但随着 Reflection、Stop Hook、Planner、异步、回放、恢复这些能力加入，两个裸列表会很快变得不够清楚。比如：

- Reflection 提示应该给模型看，但不应该写进真实对话历史；
- 工具 Observation 应该给模型继续处理，也应该在最终提交时写入本轮历史；
- 流式输出中断时，用户消息和半截 assistant 输出都不应该被错误提交；
- 上下文压缩后的模型视图不应该覆盖原始完整历史；
- 后续 Checkpoint / Replay 需要知道哪些消息已经提交，哪些还只是本轮临时状态。

所以 6.4 的目标不是“让模型变聪明”，而是把 Agent 内部的消息账本理清楚：

```text
哪些消息已经是历史？
哪些消息只是当前运行视图？
哪些消息本轮结束后才能提交？
哪些消息是这一次真正发给模型的上下文？
```

一句话总结：

```text
6.4 = 把 AgentLoop 里的消息列表拆成明确分层，防止中断、Reflection、工具调用和后续恢复逻辑把历史写乱。
```

## 1. ConversationMessageStore 是什么

对应代码：

- `zzm_agent/core/runtime_messages.py`
  - `class ConversationMessageStore`

`ConversationMessageStore` 是当前 Turn 的运行时消息账本。它不替代 `MemoryStore`，而是位于 `AgentLoop` 和 `MemoryStore` 之间：

```text
AgentLoop
→ ConversationMessageStore
→ MemoryStore.append(...)
```

它负责决定：

- 哪些消息进入模型上下文；
- 哪些消息只是运行时临时使用；
- 哪些消息等待本轮完成后提交；
- 哪些消息已经提交到历史。

当前字段：

```text
ConversationMessageStore
├── persisted_messages
├── runtime_messages
├── pending_messages
├── model_context_messages
└── committed_messages
```

## 2. persisted_messages：已经提交的历史

对应字段：

- `ConversationMessageStore.persisted_messages`

含义：

```text
已经原子提交过、属于真实会话历史的消息。
```

来源：

```text
self.store.load_history()
```

注意：6.4 不改变 `MemoryStore` 的持久化格式，只是在运行时复制一份已提交历史视图，方便后续恢复、回放和消息边界检查。

## 3. runtime_messages：当前运行视图

对应字段：

- `ConversationMessageStore.runtime_messages`

含义：

```text
当前 ReAct Loop 内部正在使用的完整运行视图。
```

它包含：

- 当前模型上下文；
- assistant tool call 意图；
- tool Observation；
- Reflection 运行时提示；
- 最终 assistant 回复。

重要点：

```text
runtime_messages 里面的消息不一定都会持久化。
```

比如 Reflection 提示会进入 `runtime_messages`，因为模型下一轮需要看到它；但它不会进入 `pending_messages`，所以不会写入真实历史。

## 4. pending_messages：当前 Turn 待提交消息

对应字段：

- `ConversationMessageStore.pending_messages`

含义：

```text
当前用户 Turn 中，只有当本轮安全结束后才允许写入历史的消息。
```

典型内容：

```text
user message
assistant tool_call intent
tool message / Observation
final assistant message
```

正常完成时：

```text
message_store.commit(self.store.append)
```

中断时：

```text
message_store.rollback_pending()
```

这保证了一个原则：

```text
中断只回滚本轮 pending_messages，不破坏已经提交的 persisted_messages。
```

## 5. model_context_messages：真正发给模型的视图

对应字段：

- `ConversationMessageStore.model_context_messages`

对应方法：

- `ConversationMessageStore.prepare_model_context()`

含义：

```text
某一次模型调用实际使用的 messages。
```

每次调用模型前，`AgentLoop` 都会执行：

```text
model_context_messages = message_store.prepare_model_context()
```

然后把这个冻结后的视图传给：

- `_save_context_snapshot(...)`
- `_complete_once(...)`
- `_stream_once(...)`
- `_estimate_call_usage(...)`

这样做的好处是：

- 模型看到的上下文有明确快照；
- 后续 runtime_messages 再变化，不会反向污染已经记录的模型请求；
- 上下文压缩只影响模型视图，不覆盖真实历史。

## 6. Reflection 为什么是 runtime-only

对应代码：

- `zzm_agent/core/agent_loop.py`
  - `_request_reflection()`
- `zzm_agent/core/runtime_messages.py`
  - `ConversationMessageStore.append_runtime_only()`

6.4 把 Reflection 提示改成：

```text
message_store.append_runtime_only(...)
```

这表示：

```text
Reflection 提示要给模型看，但不写入真实会话历史。
```

原因是 Reflection 是 Agent 自己的运行时纠偏指令，不是用户说的话，也不是 assistant 最终对用户说的话。它如果被持久化，会污染后续会话历史。

## 7. AgentLoop 接入后的执行链路

对应代码：

- `zzm_agent/core/agent_loop.py`
  - `AgentLoop.run()`

现在单轮执行的消息链路是：

```text
store.build_turn_messages(...)
→ 得到压缩后的初始模型上下文

ConversationMessageStore.begin_turn(...)
→ persisted_messages = store.load_history()
→ runtime_messages = 初始模型上下文
→ pending_messages = 当前 user message

每次模型调用前：
→ prepare_model_context()
→ _save_context_snapshot(...)
→ _complete_once(...) 或 _stream_once(...)

模型普通回复：
→ append_pending(final assistant message)
→ commit(store.append)

模型请求工具：
→ append_pending(assistant tool_call intent)
→ 执行工具
→ append_pending(tool result message)
→ 下一轮模型调用

Reflection：
→ append_runtime_only(reflection system prompt)
→ 下一轮模型调用

中断：
→ rollback_pending()
→ 不写入 MemoryStore
```

## 8. 6.4 和 6.3 的关系

6.3 解决的是：

```text
Loop 当前执行到哪个阶段，以及为什么跳转。
```

6.4 解决的是：

```text
每个阶段产生的消息应该放在哪一层，以及什么时候提交。
```

比如工具调用阶段：

```text
6.3：LoopPhase.EXECUTING_TOOLS / PROCESSING_OBSERVATIONS
6.4：assistant tool_call intent 和 tool result 进入 pending_messages
```

比如 Reflection 阶段：

```text
6.3：LoopPhase.REFLECTING
6.4：Reflection prompt 进入 runtime_messages，但不进入 pending_messages
```

## 9. 6.4 没有做什么

6.4 只做运行时消息分层，不做下面这些事情：

- 不改变 `MemoryStore` 的磁盘格式；
- 不实现完整 CheckpointStore，这留到 6.11；
- 不实现状态序列化和版本迁移，这留到 6.16；
- 不实现 Planner 的任务级消息隔离，这留到 P4；
- 不实现异步消息提交，这留到 P6。

## 10. 测试位置和验证结果

测试文件：

- `tests/test_runtime_messages.py`
- `tests/test_runtime_state.py`

覆盖内容：

- `runtime_messages`、`pending_messages`、`model_context_messages` 分层互不混淆；
- `append_runtime_only()` 进入模型上下文但不进入提交历史；
- `commit()` 只提交 pending 消息，并清空 pending；
- `rollback_pending()` 只回滚本轮 pending，不破坏 persisted；
- 输入消息会被复制，外部修改不会污染账本；
- `AgentLoop` 简单回复会提交 user + assistant；
- `AgentLoop` 工具调用会提交 user + assistant tool_call + tool result + final assistant；
- Reflection prompt 会留在 runtime，但不会写入 committed history。
