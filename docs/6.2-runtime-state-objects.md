# 6.2 ApplicationState / ConversationState / TurnState / LoopState 说明

## 这项工作整体在做什么

6.1 已经定义了“状态产权规则”：哪些状态存在、谁拥有、谁能改、活多久、存在哪里、坏了怎么恢复。6.2 做的是下一步：把这些规则变成代码里真正可以使用的状态对象。

可以把 6.1 和 6.2 的关系理解成：

```text
6.1 = 画状态户口本和产权规则
6.2 = 按户口本创建真正的状态对象
```

之前 `AgentLoop` 里有不少运行时字段：

- `last_turn_usage`
- `last_context_window`
- `last_progress_signal`
- `last_reflection_count`
- 工具迭代次数；
- Reflection 次数；
- 工具 Observation；
- 当前 Turn 的最终回复或错误。

这些字段短期内能工作，但它们缺少清晰的作用域。比如 `last_reflection_count` 到底属于整个会话、当前用户 Turn，还是当前 ReAct Loop？6.2 的目标就是开始把这些东西放进明确的状态对象里。

一句话总结：

```text
6.2 = 新增正式运行时状态对象，并让 AgentLoop 开始把真实执行数据同步进去。
```

## 执行链路总览

6.2 当前形成的链路是：

```text
ApplicationState
→ get_or_create_conversation(session_id)
→ ConversationState
→ start_turn(user_input)
→ TurnState
→ start_loop()
→ LoopState

AgentLoop.run()
→ 创建 TurnState / LoopState
→ 模型调用时记录 model_iterations
→ 工具执行后记录 tool_iterations 和 observations
→ Reflection 时记录 progress_signal 和 reflection_count
→ 最终回复时标记 TurnState completed / blocked / cancelled
```

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `ApplicationState`
  - `ConversationState`
  - `TurnState`
  - `LoopState`
  - `TurnStatus`
  - `LoopPhase`
- `zzm_agent/core/agent_loop.py`
  - `self.last_turn_state`
  - `self.last_loop_state`
  - `AgentLoop.run()` 中创建和同步状态对象；
  - `_request_reflection()` 中同步 Reflection 状态；
  - `_commit_turn_usage()` 中同步 TurnState usage。
- `tests/test_runtime_state.py`
  - 状态对象单元测试；
  - AgentLoop 状态集成测试。

## 1. ApplicationState

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `class ApplicationState`

这个功能做什么：

`ApplicationState` 是进程级状态对象，用来承载整个应用运行期间共享的顶层状态。

当前字段：

- `configuration`
- `model_registry`
- `tool_registry`
- `skill_registry`
- `mcp_connections`
- `active_session_id`
- `conversations`

当前方法：

- `set_active_session(session_id)`
- `get_or_create_conversation(session_id)`
- `active_conversation()`

它对应 6.1 里的生命周期规则：

- scope：`APPLICATION`
- owner：`ApplicationRuntime`
- lifetime：进程级；
- persistence：内存态；
- recovery：重启后重新创建。

为什么要这样做：

后续 QueryEngine、MCP、Skills、多 Provider 都需要一个进程级状态入口。`ApplicationState` 先提供这个容器，但不提前实现 QueryEngine。

## 2. ConversationState

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `class ConversationState`

这个功能做什么：

`ConversationState` 是会话级状态对象，跨多个用户 Turn 存在。

当前字段：

- `session_id`
- `messages`
- `usage`
- `permissions`
- `file_reads`
- `skills`
- `memories`
- `cancellation`
- `active_turn`
- `active_task`

当前方法：

- `append_messages(messages)`
- `start_turn(user_input, turn_id=None)`
- `finish_turn(final_response, messages=None, usage=None)`
- `fail_turn(error)`

它对应 6.1 里的生命周期规则：

- scope：`CONVERSATION`
- owner：`QueryEngine`
- lifetime：session；
- persistence：session store；
- recovery：resume。

为什么要这样做：

现在会话历史主要在 `MemoryStore` 里，AgentLoop 又自己维护当前 Turn 的局部变量。`ConversationState` 是未来统一 QueryEngine 的核心：它会成为跨 Turn 状态的拥有者。

## 3. TurnState

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `class TurnState`
  - `class TurnStatus`

这个功能做什么：

`TurnState` 表示一次用户输入从开始到结束的完整状态。

当前字段：

- `turn_id`
- `user_input`
- `status`
- `usage`
- `discovered_skills`
- `loaded_memory_paths`
- `permission_requests`
- `permission_denials`
- `artifacts`
- `loop`
- `final_response`
- `error`

当前方法：

- `start()`
- `start_loop()`
- `add_usage(usage)`
- `complete(final_response, usage=None)`
- `block(final_response, reason="blocked")`
- `fail(error)`
- `cancel(reason="cancelled")`

状态枚举：

- `pending`
- `in_progress`
- `completed`
- `blocked`
- `cancelled`
- `failed`

它对应 6.1 里的生命周期规则：

- scope：`TURN`
- owner：`QueryEngine`
- lifetime：单次用户 Turn；
- persistence：checkpoint store；
- recovery：rollback pending。

为什么要这样做：

一次用户输入里会发生很多事情：模型调用、工具调用、权限请求、Artifact、错误、最终回复。`TurnState` 让这些东西有一个明确归属，不再散落在函数局部变量里。

## 4. LoopState

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `class LoopState`
  - `class LoopPhase`

这个功能做什么：

`LoopState` 表示一个 Turn 内部的 ReAct Loop 状态。

当前字段：

- `phase`
- `transition`
- `model_iterations`
- `tool_iterations`
- `reflection_count`
- `current_tool_calls`
- `observations`
- `progress_signal`
- `needs_follow_up`
- `stop_hook_active`
- `stop_hook_attempts`

当前方法：

- `transition_to(phase, reason=None)`
- `record_model_call()`
- `record_tool_round(tool_calls, observations)`
- `record_progress_signal(signal)`
- `record_reflection(signal)`
- `mark_completed(reason="completed")`
- `mark_blocked(reason="blocked")`
- `activate_stop_hook()`
- `clear_stop_hook()`

当前 `LoopPhase` 是 6.2 的最小阶段枚举：

- `idle`
- `calling_model`
- `executing_tools`
- `reflecting`
- `completed`
- `blocked`
- `cancelled`
- `failed`

注意：

6.3 会做更完整的正式状态机，所以 6.2 这里只提供最小可用 phase，不提前实现完整 `LoopTransition` 规则。

为什么要这样做：

P0 中的 `last_progress_signal` 和 `last_reflection_count` 实际上都属于 ReAct Loop，而不是整个 Agent。`LoopState` 让这些字段有了正确归属。

## 5. AgentLoop 最小集成

对应代码：

- `zzm_agent/core/agent_loop.py`
  - `self.last_turn_state`
  - `self.last_loop_state`
  - `AgentLoop.run()`
  - `AgentLoop._request_reflection()`
  - `AgentLoop._commit_turn_usage()`

这个功能做什么：

`AgentLoop` 现在会在每次 `run()` 开始时创建：

```text
TurnState
└── LoopState
```

并同步以下真实运行数据：

- 模型调用次数 → `LoopState.model_iterations`
- 工具轮次数 → `LoopState.tool_iterations`
- 工具 Observation → `LoopState.observations`
- ProgressSignal → `LoopState.progress_signal`
- Reflection 次数 → `LoopState.reflection_count`
- Turn usage → `TurnState.usage`
- 最终回复 → `TurnState.final_response`
- Turn 状态 → `completed / blocked / cancelled`

为什么还保留旧字段：

旧字段如 `last_turn_usage`、`last_context_window`、`last_progress_signal`、`last_reflection_count` 仍被 CLI、测试和 eval runner 使用。6.2 采用兼容迁移，不直接删除旧字段。

后续 6.17/6.18 引入 QueryEngine 和 CLI 迁移后，再逐步让外部入口读取正式状态对象。

## 6. ConversationState 的 Turn 生命周期控制

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `ConversationState.start_turn()`
  - `ConversationState.finish_turn()`
  - `ConversationState.fail_turn()`

这个功能做什么：

`ConversationState` 可以创建、完成和失败一个 Turn，并且禁止同一 Conversation 同时开启两个 active Turn。

为什么要这样做：

跨 Turn 的所有权应该属于 Conversation，而不是 AgentLoop。现在先把基础控制方法放好，后续 QueryEngine 可以直接使用。

## 7. 和 6.1 生命周期规则的连接

对应代码：

- `zzm_agent/core/runtime_state.py`
  - 每个状态类的 `scope`
  - 每个状态类的 `policy()`
- `zzm_agent/core/state_lifecycle.py`
  - `get_state_policy()`

这个功能做什么：

每个状态类都可以通过 `policy()` 查询 6.1 定义的生命周期规则。

示例：

```text
ConversationState.policy()
→ owner = QueryEngine
→ persistence = SESSION_STORE
→ recovery = RESUME
```

为什么要这样做：

这样 6.2 的真实状态对象不会和 6.1 的设计规则脱节。后续如果实现状态序列化、QueryEngine 或恢复协议，可以直接从 policy 中读取约束。

## 8. 6.2 专项测试

对应代码：

- `tests/test_runtime_state.py`

覆盖场景：

- `ApplicationState` 创建和激活 Conversation；
- `ConversationState` 开启和完成 Turn；
- 同一 Conversation 禁止重叠 active Turn；

```

```

## 9. 6.2 和 6.3 的边界

6.2 做的是：

- 定义正式状态对象；
- 提供基础状态方法；
- 让 AgentLoop 同步真实执行数据；
- 保持旧字段兼容；
- 用测试固定状态对象行为。

6.2 不做的是：

- 不实现完整 Loop 状态机；
- 不实现非法状态转换校验；
- 不实现 `needs_follow_up` 的正式状态转移规则；
- 不实现 Stop Hook 执行机制；
- 不实现 QueryEngine；
- 不迁移 CLI 到 QueryEngine。

这些属于后续任务：

- 6.3：LoopPhase / LoopTransition 正式状态机；
- 6.10：Hook / Stop Hook；
- 6.17：QueryEngine；
- 6.18：CLI 迁移到 QueryEngine。
