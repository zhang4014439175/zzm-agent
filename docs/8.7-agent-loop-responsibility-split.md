# 8.7 AgentLoop 职责拆分

## 一句话说明

以前一次对话从准备上下文到调用模型、执行工具和错误恢复，几乎都由同一个超大运行循环处理，修改其中一处容易影响其他环节。本次把模型通信、工具执行、恢复规则和上下文准备分成四个独立部分。用户使用方式没有变化，但后续排查流式输出、工具重试或上下文问题时，可以单独验证对应环节，减少无关行为被改坏的风险。

## 为什么需要它

AgentLoop 是一轮 Agent 执行的核心。它既要维护当前执行状态，又直接处理模型接口差异、流式片段、工具权限、自动重试、反思提示和上下文预算。

这些事情互相关联，但不是同一种职责。例如，调整某个模型供应商的流式返回格式，不应该同时触碰文件工具权限；修改上下文预算，也不应该改变错误恢复文案。把所有代码放在一个类里，会让测试难以指出究竟是哪一层出错。

本次拆分不增加新的用户命令。它把已有行为放到清晰边界中，并让 AgentLoop 只负责安排一次执行段从开始走到完成、让出、阻塞、失败或取消。

## 一个实际使用例子

用户输入：“读取 `README.md`，然后总结项目的安装方法。”

1. 系统先准备本轮上下文，把系统提示、历史消息、用户问题、工具说明和输出预留统一核算。临时运行指令只在本轮可见，不写入历史。
2. 模型通信部分发送请求。模型以流式方式先返回文字片段，再返回一个 `read_file` 工具调用。系统按顺序组装这些片段，不把半截参数当成完整调用。
3. 工具协调部分校验调用并判断风险。读取文件属于低风险操作，可以直接执行；如果换成高风险工具，则会沿用原来的确认流程。
4. 文件内容返回后，运行循环把结果作为观察信息交回模型，并继续维护本轮状态和用量。
5. 如果工具临时超时，恢复规则决定是否重试以及等待多久；如果模型反复做同一件事，则生成明确的停止或反思提示。
6. 模型最终给出安装方法摘要。AgentLoop 把本轮标记为完成，并按原方式保存消息和用量。

用户看到的流式文字、工具确认和最终回复与拆分前一致。变化发生在内部边界和可测试性上。

## 功能的大致流程

1. 用户提交消息，系统开始一个新的执行段。
2. 上下文准备环节选择历史、记忆和临时指令，计算工具说明及输出所需空间。固定内容已超出窗口时，执行会明确阻塞。
3. AgentLoop 创建本轮状态、取消令牌和生命周期 Hook，然后请求模型。
4. 模型通信环节统一处理普通回复和流式回复，并整理正文、推理片段、用量、结束原因和工具调用。
5. 如果模型没有请求工具，AgentLoop 检查空回复、完成条件和停止 Hook，随后完成或进入有限恢复。
6. 如果模型请求工具，工具协调环节执行参数校验、权限确认、取消检查和有限重试。
7. 工具结果回填后，AgentLoop 检查重复调用和无进展信号。首次停滞可要求模型换一种方法，继续停滞则安全停止。
8. 达到单段工具轮次或上下文边界时，系统保存检查点并让 QueryEngine 自动续段，不把内部换段误报为任务完成。
9. 所有路径最终进入完成、让出、阻塞、失败或取消之一，并保留原消息、事件和 Replay 行为。

## 开发前和开发后的区别

开发前：

- AgentLoop 直接处理模型请求、流解析、工具权限、重试、恢复文案和上下文预算。
- 单独测试某个环节时，经常需要构造整个运行循环。
- 修改供应商响应或上下文规则容易触碰大量无关代码。

开发后：

- 模型请求和流解析由独立模型轮次驱动器处理。
- 工具确认、取消兼容和重试由工具协调器处理。
- 反思、停止文案和退避时间由恢复策略集中决定。
- 上下文选择、工具预算和临时消息由上下文准备服务处理。
- AgentLoop 保留执行顺序、状态转换、Hook、用量和 Segment 终止编排。
- 原私有兼容入口继续存在并委托新组件，旧调用方无需同步重写。

## 现在已经支持的能力

- 独立测试流式和非流式模型轮次。
- 统一组装正文、推理内容、用量和工具调用增量。
- 集中处理工具风险确认、权限状态、取消和有限重试。
- 集中处理重复调用、无进展、反思和重试退避规则。
- 统一核算历史消息、工具说明、临时指令和输出预留。
- 临时运行指令只影响当前模型请求，不进入持久历史。
- 保持 AgentLoop、CLI、QueryEngine 和 Replay 的既有调用方式。

## 当前限制（还做不到什么）

- AgentLoop 仍负责完整的单 Segment 状态编排，本任务没有把它改成异步运行循环。
- 工具仍按顺序执行，没有增加并发调度。
- ToolRegistry 的注册、插件加载和目录结构没有在本任务中继续拆分。
- RuntimeState 文件拆分属于 8.8，工作区副作用统一属于 8.9。
- 本次是职责重构，不会让模型本身回答得更聪明，也不新增 CLI 功能。

## 给开发者看的实现位置

- `zzm_agent/core/model_turn.py`
  - `ModelTurnDriver`：发送模型请求，解析普通或流式返回，并组装工具调用。
- `zzm_agent/core/tool_coordinator.py`
  - `ToolCallCoordinator`：执行权限确认、Registry 兼容调用、取消检查和有限重试。
- `zzm_agent/core/recovery_policy.py`
  - `RecoveryPolicy`：生成停止与反思提示，并计算有上限的退避时间。
- `zzm_agent/core/context_preparation.py`
  - `ContextPreparationService`：构建系统提示、工具 Schema 预算、输出预留和分层消息。
- `zzm_agent/core/agent_loop.py`
  - 装配四个组件，保留 Turn/Loop 生命周期、Hook、Usage、ProgressMonitor 和 Segment 结果编排。

执行链路：

```text
用户输入
→ ContextPreparationService 准备模型上下文
→ AgentLoop 建立本轮状态
→ ModelTurnDriver 请求并解析模型
→ ToolCallCoordinator 执行获准工具
→ RecoveryPolicy 提供恢复或停止决策文本
→ AgentLoop 完成、让出、阻塞、失败或取消
```

## 测试如何证明它有效

`tests/test_model_turn.py` 验证模型轮次驱动器与旧入口共享同一适配器，普通和流式调用的参数、回调和结果顺序不变。

`tests/test_agent_loop_components.py` 验证上下文预算与临时消息分层、工具权限确认、可恢复错误重试、停止文案和退避上限。

`tests/test_agent_loop.py` 与 `tests/test_agent_replay.py` 验证真实运行循环、权限、工具回填、流式事件、错误恢复和 Replay 没有因拆分改变。

实际验证结果：

- AgentLoop 与 Replay 定向回归：`50 passed`。
- 新增组件测试：`7 passed`。
- 完整回归：`364 passed, 2 skipped`。

这些测试证明四个职责已经独立接入，同时用户可观察的模型回复、权限行为、消息历史和回放结果保持一致。
