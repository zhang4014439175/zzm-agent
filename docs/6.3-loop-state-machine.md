# 6.3 LoopPhase / LoopTransition 正式状态机说明

## 这项工作整体在做什么

6.2 已经把 ReAct 执行过程放进了 `LoopState`，但那时的 `phase` 更像一个“当前状态标签”：代码可以把它从任何状态直接改成另一个状态，缺少规则约束。

6.3 做的是把这个标签升级成真正的状态机。也就是说，ReAct Loop 不再只是“记录自己现在在哪里”，而是必须按照一条明确路线移动：

```text
准备本轮
→ 调用模型
→ 如果是流式输出，进入流式响应
→ 如果模型要调用工具，先校验工具调用
→ 必要时等待权限确认
→ 执行工具
→ 处理 Observation
→ 必要时 Reflection 或 Stop Hook
→ 再次调用模型，或者结束 / 阻塞 / 取消 / 失败
```

这项工作的价值是：后续做权限生命周期、Stop Hook、Planner、异步 Loop、并发工具调用时，不再靠散落在 `AgentLoop.run()` 里的局部变量猜当前执行到哪一步，而是可以直接看 `LoopState.phase`、`LoopState.transition` 和 `LoopState.transition_history`。

一句话总结：

```text
6.3 = 给单轮 ReAct Loop 加上正式交通规则：能去哪、为什么去、非法跳转要报错。
```

## 1. LoopPhase：Loop 当前处于哪个阶段

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `class LoopPhase`

6.3 正式引入的阶段包括：

```text
IDLE
→ PREPARING
→ CALLING_MODEL
→ STREAMING_RESPONSE
→ VALIDATING_TOOL_CALLS
→ AWAITING_PERMISSION
→ EXECUTING_TOOLS
→ PROCESSING_OBSERVATIONS
→ REFLECTING
→ RUNNING_STOP_HOOKS
→ COMPLETED / BLOCKED / CANCELLED / FAILED
```

每个阶段的含义：

- `IDLE`：Loop 刚创建，还没有开始处理当前 Turn；
- `PREPARING`：Loop 已进入当前 Turn，准备调用模型；
- `CALLING_MODEL`：正在调用模型；
- `STREAMING_RESPONSE`：模型正在流式输出；
- `VALIDATING_TOOL_CALLS`：模型返回了工具调用，正在进入工具调用校验阶段；
- `AWAITING_PERMISSION`：工具需要用户或策略确认，正在等待权限决定；
- `EXECUTING_TOOLS`：工具正在执行；
- `PROCESSING_OBSERVATIONS`：工具结果已经回来，正在作为 Observation 处理；
- `REFLECTING`：检测到无进展或重复调用后，插入 Reflection 纠偏；
- `RUNNING_STOP_HOOKS`：Stop Hook 正在阻止或改写结束流程；
- `COMPLETED`：Loop 正常完成；
- `BLOCKED`：Loop 被安全规则、无进展规则或迭代上限阻塞；
- `CANCELLED`：Loop 被用户或运行时取消；
- `FAILED`：Loop 因异常失败。

注意：6.3 只是建立 Stop Hook 的状态入口，真正完整 Hook 系统留到 6.10。

## 2. LoopTransition：为什么发生状态转换

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `class LoopTransition`

6.3 把“转换原因”也枚举化。这样后续看日志、回放、测试时，不只是知道从 `A` 到了 `B`，还能知道为什么跳过去。

当前正式原因包括：

- `next_turn`：开始处理当前用户 Turn；
- `tool_follow_up`：工具执行后，需要再次调用模型处理 Observation；
- `reflection_retry`：Reflection 后重新调用模型；
- `stop_hook_retry`：Stop Hook 阻止结束后重新调用模型；
- `completed`：正常完成；
- `no_progress`：检测到无进展；
- `iteration_limit`：达到最大工具迭代次数；
- `duplicate_call_limit`：达到重复工具调用熔断阈值；
- `permission_denied`：权限被拒绝；
- `blocked`：一般阻塞；
- `cancelled`：取消；
- `error`：异常失败；
- `stream_response`：进入流式响应；
- `tool_validation`：进入工具调用校验；
- `permission_requested`：发起权限确认；
- `tool_execution`：开始执行工具；
- `observation`：开始处理工具 Observation。

路线图要求的转换原因已经全部包含；后面几个是为了让内部执行链路更可观察。

## 3. 合法转换表：防止 Loop 乱跳

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `_ALLOWED_LOOP_TRANSITIONS`
  - `LoopState.can_transition_to()`
  - `LoopState.transition_to()`

状态机的核心规则在 `_ALLOWED_LOOP_TRANSITIONS` 中。

举例：

```text
IDLE 可以进入 PREPARING
PREPARING 可以进入 CALLING_MODEL
CALLING_MODEL 可以进入 STREAMING_RESPONSE / VALIDATING_TOOL_CALLS / COMPLETED
VALIDATING_TOOL_CALLS 可以进入 AWAITING_PERMISSION / EXECUTING_TOOLS / REFLECTING
PROCESSING_OBSERVATIONS 可以进入 CALLING_MODEL / REFLECTING / RUNNING_STOP_HOOKS
终态 COMPLETED / BLOCKED / CANCELLED / FAILED 不能再跳回执行态
```

如果代码试图从 `IDLE` 直接跳到 `EXECUTING_TOOLS`，会抛出：

```text
LoopTransitionError
```

这能提前暴露运行时编排错误。比如后续做并发工具调用时，如果没有先经过工具校验就直接执行工具，测试会立刻失败。

## 4. LoopState 新增和调整的关键方法

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `class LoopState`

关键方法：

- `prepare_next_turn()`：进入 `PREPARING`；
- `record_model_call()`：进入 `CALLING_MODEL`，并增加 `model_iterations`；
- `record_streaming_response()`：进入 `STREAMING_RESPONSE`；
- `validate_tool_calls(tool_calls)`：进入 `VALIDATING_TOOL_CALLS`；
- `await_permission()`：进入 `AWAITING_PERMISSION`；
- `record_permission_denial()`：记录权限拒绝转换原因；
- `record_tool_execution_start(tool_calls)`：进入 `EXECUTING_TOOLS`；
- `record_tool_round(tool_calls, observations)`：记录一轮工具结果并进入 `PROCESSING_OBSERVATIONS`；
- `record_progress_signal(signal)`：记录无进展信号；
- `record_reflection(signal)`：进入 `REFLECTING` 并增加 `reflection_count`；
- `activate_stop_hook()`：进入 `RUNNING_STOP_HOOKS` 并增加 `stop_hook_attempts`；
- `mark_completed()`：进入 `COMPLETED`；
- `mark_blocked()`：进入 `BLOCKED`；
- `mark_cancelled()`：进入 `CANCELLED`；
- `mark_failed()`：进入 `FAILED`。

同时新增：

- `transition_history`

它会记录每次转换：

```text
from: 从哪个阶段来
to: 到哪个阶段去
reason: 为什么转换
```

这对后续回放、调试、UI 展示都很重要。

## 5. AgentLoop 如何接入状态机

对应代码：

- `zzm_agent/core/agent_loop.py`
  - `AgentLoop.run()`
  - `_request_reflection()`

当前接入链路如下：

```text
TurnState.start_loop()
→ LoopState.prepare_next_turn()

AgentLoop.run()
→ loop_state.record_model_call()
→ 如果 stream=True，则 loop_state.record_streaming_response()
→ 模型返回最终文本：turn_state.complete()
→ 模型返回 tool_calls：loop_state.validate_tool_calls()
→ 工具需要确认：loop_state.await_permission()
→ 权限被拒绝：loop_state.record_permission_denial()
→ 工具开始执行：loop_state.record_tool_execution_start()
→ 工具结果返回：loop_state.record_tool_round()
→ 检测到无进展：loop_state.record_progress_signal()
→ 需要纠偏：loop_state.record_reflection()
→ 达到迭代上限或重复调用熔断：turn_state.block()
```

这条链路把原来隐含在 `while True` 里的执行阶段显式化了。

## 6. needs_follow_up 的作用

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `LoopState.needs_follow_up`
  - `LoopState.record_tool_round()`
  - `LoopState.mark_completed()`
  - `LoopState.mark_blocked()`

`needs_follow_up` 表示：

```text
工具 Observation 已经产生，模型还需要再被调用一次来理解这些结果。
```

它在工具结果返回后变成 `True`：

```text
record_tool_round()
→ needs_follow_up = True
```

当最终完成、阻塞、取消或失败时，它会被清掉：

```text
mark_completed()
mark_blocked()
mark_cancelled()
mark_failed()
→ needs_follow_up = False
```

后续 Planner、Async Loop、UI Renderer 都可以用它判断当前 Loop 是“已经结束”还是“工具结果还没被模型消化”。

## 7. stop_hook_active 和 stop_hook_attempts 的作用

对应代码：

- `zzm_agent/core/runtime_state.py`
  - `LoopState.stop_hook_active`
  - `LoopState.stop_hook_attempts`
  - `LoopState.activate_stop_hook()`
  - `LoopState.clear_stop_hook()`

这两个字段是为 6.10 Hook 系统提前铺底：

- `stop_hook_active`：当前是否有 Stop Hook 正在阻止结束；
- `stop_hook_attempts`：Stop Hook 已经尝试阻止多少次。

它们解决的是一个典型问题：

```text
模型想结束
→ Stop Hook 觉得还不能结束，要求继续
→ 模型又想结束
→ Stop Hook 又阻止
→ 如果没有 attempts 上限，就可能无限阻塞
```

6.3 还没有实现完整 Stop Hook，只是先把状态位和合法阶段放进 `LoopState`，避免后面再补 Hook 时没有状态承载点。

## 8. 和 6.2 的关系

6.2 做的是：

```text
把状态对象建出来
```

6.3 做的是：

```text
给 LoopState 的 phase 加规则
```

所以 6.3 没有推翻 6.2，而是在 6.2 的基础上补上了：

- 状态阶段更完整；
- 转换原因更清楚；
- 非法转换会报错；
- 转换历史可追踪；
- `AgentLoop.run()` 在更多关键点同步状态。

## 10. 6.3 没有做什么

为了边界清晰，6.3 只做 Loop 状态机，不做下面这些事情：

- 不实现完整 Hook 系统，这留到 6.10；
- 不实现消息分层，这留到 6.4；
- 不实现完整 UsageState，这留到 6.5；
- 不实现完整 PermissionState，这留到 6.6；
- 不实现异步 Loop 或并发工具调用，这留到 P6。

这样做的原因是：状态机必须先稳定下来，后续功能才能可靠地挂在同一套状态规则上。
