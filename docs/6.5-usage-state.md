# 6.5 完整 UsageState 及多作用域累计说明

6.5 做的是把“本轮花了多少 Token”升级成一套正式账本。

在 6.5 之前，项目里已经有 `last_turn_usage` 和 `cumulative_usage`，CLI 可以看到本轮和累计 Token。但这些字段更像展示用计数器：它们不知道这笔消耗属于哪个模型、哪个 Turn、哪个 Conversation，也没有正式记录 cache、reasoning、工具 Schema、模型调用次数和工具调用次数。后续要做 Planner、Task、Session 恢复和费用审计时，只靠两个计数器很容易串账。

所以 6.5 的目标不是改变 Agent 的回答能力，而是让运行时用量可归属、可累计、可序列化：

- 本轮 Turn 用了多少；
- 当前 Conversation / Session 累计多少；
- 当前 Task 累计多少；
- 整个应用运行期累计多少；
- 每个模型分别用了多少；
- 这其中有多少 input / output / cache / reasoning / tool schema token；
- 发生了多少次模型调用和工具调用。

一句话概括：6.5 = 给模型调用和工具调用建立正式用量账本，后续 Planner、Task、Session 持久化和成本展示都从这里取数。

## 2. TokenUsage 扩展了什么

位置：`zzm_agent/core/observability.py`

`TokenUsage` 原来主要记录：

- `prompt_tokens`
- `completion_tokens`
- `total_tokens`
- `source`

6.5 新增：

- `cache_creation_tokens`：写入缓存的 token 数；
- `cache_read_tokens`：从缓存命中的 token 数；
- `reasoning_tokens`：模型推理 token 数；
- `tool_schema_tokens`：工具 schema 占用的上下文 token 数；
- `model_calls`：模型调用次数；
- `tool_calls`：工具调用次数；
- `to_record()` / `from_record()`：支持序列化和恢复。

旧字段没有删除，所以 CLI、测试和现有统计仍然可以继续使用 `last_turn_usage.prompt_tokens`、`last_turn_usage.total_tokens` 这类字段。

## 3. UsageState 是什么

位置：`zzm_agent/core/observability.py`

新增 `UsageState`，它负责把一次调用的 `TokenUsage` 同时累计到多个作用域：

```text
UsageState
├── turn
├── conversation
├── task
├── application
├── by_model
├── current_turn_id
├── conversation_id
└── task_id
```

关键方法：

- `start_turn(turn_id)`：开始新 Turn，清空 Turn 级别统计；
- `set_conversation(conversation_id)`：绑定当前 Session / Conversation；
- `set_task(task_id)`：绑定当前 Task，给后续 Planner 预留；
- `record_model_call(usage, model, tool_schema_tokens=0)`：记录一次模型调用，并同步累计到 Turn、Conversation、Task、Application 和对应模型；
- `record_tool_calls(count)`：记录工具调用次数；
- `snapshot(scope)`：读取某个作用域的用量快照；
- `snapshot_for_model(model)`：读取某个模型的用量快照；
- `to_record()` / `from_record()`：把完整账本转成普通 dict，供后续 Session / Task 持久化使用。

## 4. RuntimeState 如何接入

位置：`zzm_agent/core/runtime_state.py`

6.5 在状态对象中补充了 `usage_state`：

- `TurnState.usage_state`
- `ConversationState.usage_state`
- `ApplicationState.usage_state`

其中：

- `TurnState.start()` 会调用 `usage_state.start_turn(turn_id)`；
- `TurnState.complete(..., usage=...)` 会把最终 Turn usage 同步进 `usage_state.turn`；
- `ConversationState.finish_turn(..., usage=...)` 会把 usage 同步累计进 `usage_state.conversation`；
- `ApplicationState.usage_state` 先作为应用级账本入口预留，后续 QueryEngine 接入后可以统一累计所有会话。

这样 6.5 没有强行引入 QueryEngine，也没有提前做 Session 状态持久化，但已经把后续要持久化的状态结构准备好了。

## 5. Session 持久化如何接入

位置：`zzm_agent/memory/store.py`

6.5 在 `MemoryStore` 中新增：

- `save_usage_state(usage_state)`：把当前 UsageState 写入当前 Session 的 `meta.json`；
- `load_usage_state()`：从当前 Session 的 `meta.json` 读取 UsageState。

写入位置在每个 Session 自己的元数据里：

```text
sessions/<session-id>/meta.json
└── usage_state
```

这样切换到 `alpha` Session 时读取的是 `alpha/meta.json`，切换到 `beta` Session 时读取的是 `beta/meta.json`，不会把一个会话的 token 账本带到另一个会话里。

## 6. AgentLoop 如何记录用量

位置：`zzm_agent/core/agent_loop.py`

`AgentLoop` 新增：

```python
self.usage_state = UsageState()
```

每次 `run()` 开始时：

- 如果 `store` 支持 `load_usage_state()`，先从当前 Session 恢复 UsageState；
- 用当前 `turn_state.turn_id` 调用 `self.usage_state.start_turn(...)`；
- 如果 `store` 有 `session_id`，调用 `self.usage_state.set_conversation(...)`；
- 把 `turn_state.usage_state` 指向当前 `UsageState`。

每次模型调用完成后：

1. 先从 SDK 返回中读取 usage；
2. 如果 SDK 没有返回 usage，就走原来的估算逻辑；
3. 调用 `self.usage_state.record_model_call(...)`；
4. 把返回的 accounted usage 累计进本轮 `turn_usage`。

这一步会记录：

- input / output tokens；
- cache read / cache creation tokens；
- reasoning tokens；
- tool schema tokens；
- 模型调用次数；
- 按模型名累计。

当模型返回 tool calls 时：

```python
tool_count_usage = self.usage_state.record_tool_calls(len(tool_calls_raw))
turn_usage.add(tool_count_usage)
```

这会把工具调用次数计入 Turn、Conversation、Task 和 Application，但不会污染 token 来源。也就是说，模型 usage 仍然可以保持 `api` 或 `estimated`，不会因为工具计数变成 `mixed`。

Turn 提交时，`_commit_turn_usage()` 会继续同步旧字段，同时在 store 支持时调用：

```python
store.save_usage_state(self.usage_state)
```

这一步负责把 UsageState 写回当前 Session 的 `meta.json`。

## 7. SDK Usage 兼容

位置：`AgentLoop._usage_from_sdk_object()`

6.5 继续兼容 OpenAI 兼容格式：

- `prompt_tokens`
- `completion_tokens`
- `total_tokens`

并额外读取：

- `prompt_tokens_details.cached_tokens`
- `prompt_tokens_details.cache_read_tokens`
- `prompt_tokens_details.cache_creation_tokens`
- `completion_tokens_details.reasoning_tokens`
- `cache_creation_input_tokens`
- `cache_read_input_tokens`

如果服务商不返回这些字段，对应值就是 0，不影响主流程。

## 8. 执行链路

一次普通 Turn 的用量链路如下：

```text
用户输入
  ↓
AgentLoop.run()
  ↓
MemoryStore.load_usage_state()
  ↓
UsageState.start_turn(turn_id)
  ↓
模型调用完成
  ↓
_usage_from_sdk_object() 或 _estimate_call_usage()
  ↓
UsageState.record_model_call()
  ↓
累计到 turn / conversation / task / application / by_model
  ↓
如果有 tool_calls，UsageState.record_tool_calls()
  ↓
Turn 完成时 _commit_turn_usage()
  ↓
last_turn_usage / cumulative_usage / TurnState.usage_state 同步
  ↓
MemoryStore.save_usage_state()
```

## 9. 和旧字段的关系

6.5 保留旧兼容字段：

- `AgentLoop.last_turn_usage`
- `AgentLoop.cumulative_usage`
- `TurnState.usage`
- `ConversationState.usage`

它们仍然服务于 CLI、底部状态栏、已有测试和历史调用方式。

新增的 `UsageState` 是更完整的内部账本。后续 QueryEngine、Task、Session 持久化、费用明细和模型维度统计应该优先接 `UsageState`。

## 11. 6.5 没有做什么

为了边界清晰，6.5 不做下面这些事情：

- 不实现完整 Task 持久化落盘，这留到 Planner / Task 状态接入阶段；
- 不改 CLI 的展示表格样式，CLI 仍使用兼容字段读取；
- 不实现 Token Budget 2.0，这留到 7.5；
- 不实现费用配置中心，只保留 `TokenUsage.estimated_cost_usd(...)` 作为计算入口；
- 不改变模型调用、工具调用和消息提交行为。

6.5 的边界就是：把 usage 账本建完整，并让 AgentLoop 正式写入这本账。
