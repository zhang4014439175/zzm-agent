# 6.11 EventBus、ArtifactStore 与 CheckpointStore

这项工作是为了让运行时发生过什么、生成了什么大结果、以及恢复时能回到哪里都有统一记录。它解决的不是“怎么把内容显示得好看”，而是先把事实留下来：Agent 当前进入了哪个阶段、调用了哪个工具、工具有没有失败、完整输出保存在哪里、当前 Turn 或 Conversation 有没有可恢复的快照。以前这些信息分散在工具回调、状态对象、日志和临时字段里，后续要做回放、恢复、桌面端进度展示或长结果治理时，很难稳定地追踪同一件事。

真实使用时，用户可能只看到一句“正在运行测试”或“测试失败，打开完整日志”。但运行时背后需要保存三类东西：第一，事件流告诉界面和日志系统“测试开始了、结束了、失败原因是什么”；第二，Artifact 保存完整 stdout/stderr 或报告文件，避免把几千行日志塞回模型上下文；第三，Checkpoint 保存关键状态，方便中断后判断能不能恢复到某个 Turn、Task 或 WorkingMemory。6.11 先建立这个事实层，展示、折叠、进度窗口和不同工具的专属渲染留给 6.12-6.15。

## 使用场景和例子

### 场景一：工具输出很长，但模型和界面只需要摘要

用户让 Agent 运行一组测试。测试命令输出了 3000 行日志，其中大部分是通过信息，最后 20 行有失败堆栈。

没有 `ArtifactStore` 时，常见做法是把完整输出直接作为 tool observation 塞回模型，结果会撑大上下文，也让 CLI 或桌面端对话流变得很难读。现在的目标是：完整日志保存为 Artifact，对话里只保留摘要、失败片段和 artifact id。

示例行为：

```text
工具完整输出：3000 行 pytest 日志
ArtifactStore 保存：artifact-abc123.txt
模型可见内容：pytest 失败，2 个测试失败，完整日志见 artifact-abc123
用户界面可见内容：测试失败，点击打开完整日志 artifact-abc123
```

对应代码入口：

```python
artifact = conversation.artifacts.save_text(
    full_stdout,
    kind="tool_result",
    summary="pytest failed: 2 failed, 240 passed",
    session_id="session-a",
    turn_id="turn-1",
    metadata={"tool_call_id": "call-1"},
)
```

### 场景二：桌面端或 CLI 想显示进度，但不能影响 Agent 执行

`EventBus` 里的“发布事件”和“接收事件”是运行时内部的通知机制，不是模型消息，也不是网络请求。

- 发布事件：核心运行时把已经发生的事实写入事件流，比如“Turn 开始”“工具开始执行”“工具执行结束”“权限被拒绝”。
- 接收事件：日志记录器、CLI 渲染器、未来桌面端 UI 等观察者订阅这些事实，用来打印日志、刷新界面或写入 JSONL。

关键约束是：接收事件的一方只是观察者，不能决定 Agent 是否继续执行。即使 UI 刷新失败或日志写入失败，也不能让工具调用失败。

示例行为：

```python
def render_event(event):
    print(event.event_type, event.payload)

conversation.events.subscribe(render_event)

conversation.events.publish(
    "tool.started",
    {"tool_name": "run_shell", "tool_call_id": "call-1"},
    session_id="session-a",
    turn_id="turn-1",
)
```

这里 `publish(...)` 是“发布事件”：运行时宣布 `run_shell` 开始执行。`render_event(...)` 是“接收事件”：CLI 或桌面端拿到这个事实后显示“正在运行 run_shell”。如果 `render_event(...)` 抛异常，异常会记录到 `observer_errors`，主流程继续执行工具。

### 场景三：长任务中断后，需要知道能恢复到哪里

用户让 Agent 修改多个文件并运行测试。执行到一半时进程退出或用户取消。恢复时不能只看聊天记录，因为聊天记录不知道哪些内部状态已经提交、哪些只是临时计算。

`CheckpointStore` 用来保存恢复点。例如：

```text
checkpoint-1：Turn 刚开始，用户输入已记录
checkpoint-2：工具调用完成，Artifact 已保存
checkpoint-3：最终回复已生成，Turn 可视为完成
```

恢复或回放时可以查询最新检查点：

```python
checkpoint = conversation.checkpoints.latest(
    scope="turn",
    session_id="session-a",
    turn_id="turn-1",
)
```

如果最新检查点停在“工具调用完成但最终回复未生成”，后续恢复逻辑就可以明确告诉用户：这个 Turn 有可恢复状态，但最终回复还没有提交。完整的版本迁移和恢复协议会在 6.16 展开，6.11 先提供可保存、可查询、带校验和的检查点账本。

## 功能作用

- `EventBus` 统一发布运行时事实事件，覆盖状态转换、模型调用、工具、权限、Hook、Usage、取消等后续事件类型。
- `ArtifactStore` 保存长工具结果、报告、Diff、日志和生成文件，并返回可放入状态对象的轻量元数据。
- `CheckpointStore` 保存 Conversation、Turn、Task 和 WorkingMemory 等状态快照，为恢复与回放提供查询入口。
- 观察者异常会被记录到 `observer_errors`，但不会向外抛出，也不会改变 Agent 行为。
- 当前阶段只定义事实记录和基础存取，不定义 UI 渲染、进度窗口、折叠策略或工具结果分层。

## 执行链路

以下链路以“运行测试并产生长日志”为例：

1. 用户提交请求后，运行时创建或取得 `ConversationState`，其中已经有 `events`、`artifacts` 和 `checkpoints`。
2. Turn 开始时，运行时可以调用 `EventBus.publish("turn.started", ...)` 发布事实事件。事件会获得单调递增的 `sequence`，方便后续按发生顺序回放。
3. CLI、JSONL 日志器或未来桌面端通过 `EventBus.subscribe(...)` 接收事件。接收事件的代码只负责观察，比如刷新状态、打印日志、落盘；它不能修改核心状态。
4. 工具开始执行时，运行时发布 `tool.started`；工具结束后发布 `tool.completed` 或 `tool.failed`。这些事件只描述已经发生的事实。
5. 如果工具输出很长，运行时调用 `ArtifactStore.save_text(...)`、`save_json(...)` 或 `save_bytes(...)` 保存完整内容，返回 `ArtifactRecord`。后续状态对象、事件或 UI 只引用 `artifact_id` 和摘要。
6. 到达关键阶段时，运行时调用 `CheckpointStore.save(...)` 保存恢复点。保存前状态会被转换成 JSON 友好的快照，并生成 `sha256` 校验和。
7. 后续恢复、回放或查看历史时，通过 `CheckpointStore.latest(...)`、`list(...)` 和 `load_from_disk()` 查询检查点，通过 `ArtifactStore.read_text(...)` 打开完整产物，通过事件记录解释执行过程。

这条链路里，“发布事件”就是核心运行时写入事实；“接收事件”就是外部观察者消费事实。二者解耦后，UI 和日志坏了不会影响 Agent 执行，Agent 执行也不需要知道未来是 CLI、桌面端还是回放器在看这些事件。

## 已知边界

- 6.11 不负责 ToolResult、ToolProgressEvent、RendererRegistry 或 DisplayMode，这些属于 6.12-6.15。
- 当前 `EventBus` 是进程内同步发布；异步事件、慢消费者背压和 UI 展示窗口会在后续进度事件与渲染协议中处理。
- `CheckpointStore` 提供基础快照保存和查询，完整状态版本迁移与恢复协议留给 6.16。
