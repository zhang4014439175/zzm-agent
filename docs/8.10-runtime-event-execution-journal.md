# 8.10 RuntimeEvent 与 ExecutionJournal

## 一句话说明

以前终端流事件、JSONL 文件和 Replay 各自保存相似但不完全相同的数据，事件顺序也只在单个内存总线里有效。本次建立了统一的版本化运行事件和执行账本。现在 CLI、JSON 输出、状态记录和 Replay 可以读取同一份事实，知道某条事件属于哪个会话和 Turn，并按稳定序号恢复原始发生顺序。

## 为什么需要它

Agent 执行时会产生“开始 Turn、输出文字、调用工具、记录用量、结束任务”等事件。终端需要这些事件展示过程，脚本需要 JSON 行，Replay 需要按原顺序重放，未来的协议入口也需要订阅相同信息。

开发前，ModelStreamEvent 主要服务终端流式展示，RuntimeEvent 由各 EventBus 自己编号，EventJsonlStore 只负责把收到的事件写入文件。不同入口可能各自重新解释事件，无法保证使用相同版本、顺序号和状态关联。

ExecutionJournal 可以理解为“只追加的执行流水账”。每条 RuntimeEvent 是其中一条带编号的事实。Schema 版本就是记录格式的版本号，用来防止新旧程序误读彼此不认识的字段。

## 一个实际使用例子

用户运行：

```text
zzm-agent exec --json "读取 README.md 并说明如何安装"
```

1. QueryEngine 创建新的 Turn，并产生 `turn.started` 状态流事件。
2. 这条流事件被转换成统一 RuntimeEvent。记录包含 `schema_version: 1`、会话 ID、Turn ID、来源和全局序号 1。
3. 模型输出正文片段时，系统继续产生 `stream.content_delta`，ExecutionJournal 分配序号 2、3 等。
4. 模型请求读取文件时，工具调用增量和工具结果也转换为相同格式，并关联到同一个 Turn。
5. CLI 的 `--json` 输出直接使用 QueryEngine 返回的 RuntimeEvent，而不是自己重新拼一套事件。
6. Turn 结束后，最终回复和终止原因也进入同一有序列表，CLI 最后输出结果行。
7. 如果之后需要排查或 Replay，系统从某个序号开始读取 Journal，即可按原顺序看到同一批事实，不会重新执行模型或文件工具。

用户得到的最终回答不变，但 JSON 事件现在拥有明确版本、顺序和状态归属。

## 功能的大致流程

1. 模型、工具或 QueryEngine 产生一个已经规范化的过程事件。
2. QueryEngine 把它转换成 RuntimeEvent，并附加会话、Turn、状态作用域、状态 ID、关联 ID 和来源。
3. EventBus 把事件交给 ExecutionJournal。Journal 分配从 1 开始、只递增不回退的序号。
4. 配置了文件路径时，Journal 立即把相同记录追加到 JSONL 文件；没有路径时仍保存在内存中。
5. EventBus 再通知终端或其他观察者。某个观察者报错只会被记录，不会让 Agent 任务失败。
6. CLI 非交互 JSON 模式读取 QueryResult 中的 RuntimeEvent，逐行输出同一记录格式。旧调用方只提供模型流事件时会安全降级。
7. 查询方可以按会话、Turn、Task、事件类型或上次序号筛选记录。
8. Replay 按序号返回已有事实，不调用模型和工具，也不修改运行状态。
9. 重新打开 Journal 时，从文件最大序号继续追加。遇到未来未知 Schema 版本时明确拒绝，避免错误解释。

## 开发前和开发后的区别

开发前：

- RuntimeEvent 没有明确 Schema 版本。
- EventBus 序号只在各自实例内有效，不同入口可能重复从 1 开始。
- CLI `--json` 直接序列化 ModelStreamEvent。
- JSONL 存储只提供简单 append/read，没有状态筛选或游标 Replay。
- 事件无法统一表达状态作用域、状态 ID、关联事件和关联执行。

开发后：

- RuntimeEvent 明确记录 Schema 版本。
- ExecutionJournal 为不同来源事件分配统一单调序号。
- 事件可关联 Session、Turn、Task 和具体状态对象。
- QueryEngine 同时保留兼容模型流事件和统一 RuntimeEvent。
- 真实 CLI JSON 输出优先使用统一事实记录。
- Journal 支持按状态关联、事件类型和序号游标查询。
- Journal 重启后继续原序号，并可按原顺序 Replay。
- 旧 `core.runtime_records` 和 EventJsonlStore 导入继续可用。

## 现在已经支持的能力

- 版本号为 1 的 RuntimeEvent 记录格式。
- 全局单调递增事件序号。
- Session、Turn、Task、状态作用域和状态 ID 关联。
- correlation ID 与 parent event ID 关联字段。
- 内存 Journal 和 JSONL 持久化 Journal。
- 按会话、Turn、Task、事件类型和序号游标查询。
- 不重新执行副作用的顺序 Replay。
- QueryEngine 自动把模型流转换为统一事实。
- CLI `exec --json` 输出统一事实并保留旧测试替身降级。
- 从旧 RuntimeEvent 记录恢复缺失的新字段。
- 拒绝当前程序无法理解的未来 Schema 版本。

## 当前限制（还做不到什么）

- ExecutionJournal 当前使用内存列表和本地 JSONL，不支持多个进程同时安全写入同一个文件。
- JSONL 发现损坏行时会明确失败，尚未提供自动隔离单行并继续读取的修复工具。
- 当前 Replay 只重放事件事实，不会自动重建完整 UI 动画，也不会重新执行模型或工具。
- correlation ID 和 parent event ID 已进入协议，但现有 QueryEngine 主要使用 Turn ID 作为关联 ID，尚未为每个嵌套工具事件建立完整父子链。
- 交互式 CLI Renderer 仍接收兼容 ModelStreamEvent；完整 CLI Runtime 目录拆分和所有入口直接消费 RuntimeEvent 属于后续 8.10A。
- SQLite 事务、索引和并发读取属于 P3.5 可选扩展，不是本任务范围。

## 给开发者看的实现位置

- `zzm_agent/runtime/events.py`
  - `RuntimeEvent`：定义版本、序号、来源、状态关联和负载的统一记录。
  - `EventBus`：发布事件、连接 Journal，并隔离观察者异常。
- `zzm_agent/runtime/journal.py`
  - `ExecutionJournal`：分配序号、追加 JSONL、恢复、筛选和 Replay。
  - `EventJsonlStore`：保留旧 append/read API，并委托统一 Journal。
- `zzm_agent/runtime/__init__.py`：提供新的运行时事件公开入口。
- `zzm_agent/core/runtime_records.py`：继续导出旧路径，同时保留 Artifact 和 Checkpoint 实现。
- `zzm_agent/core/query_engine.py`
  - `QueryResult.runtime_events`：向 CLI 和其他客户端返回本次任务的统一事实。
  - 内部 `emit()`：把 ModelStreamEvent 转换为带 Turn 关联的 RuntimeEvent。
- `zzm_agent/cli_support/runtime.py`
  - `run_exec()`：JSON 模式优先输出 QueryResult 的 RuntimeEvent。

执行链路：

```text
模型或工具产生 ModelStreamEvent
→ QueryEngine 转换为 RuntimeEvent
→ EventBus 发布
→ ExecutionJournal 分配全局序号并可选写入 JSONL
→ QueryResult 返回同一批 RuntimeEvent
→ CLI JSON 输出或 Replay 按序消费
```

## 测试如何证明它有效

`tests/test_execution_journal.py` 覆盖：

- 不同来源事件是否共享连续序号。
- 是否能按 Session、Turn 和游标筛选。
- 重启后是否从旧最大序号继续追加。
- 是否拒绝未来未知 Schema。
- QueryEngine 返回的 RuntimeEvent 是否与 Journal 中的同一批事实一致。
- 模型内容事件是否带版本、会话和 Turn 关联。

`tests/test_runtime_records.py` 验证旧 EventBus、EventJsonlStore、Artifact 和 Checkpoint API 继续工作。`tests/test_query_engine_streaming.py` 验证流事件、自动续段和完成门禁没有变化。`tests/test_cli.py` 验证 JSON 与普通终端输出兼容。

实际验证结果：

- Runtime、QueryEngine 与 CLI 定向回归：`103 passed`。
- ExecutionJournal 新增测试：`3 passed`。
- 完整回归：`374 passed, 2 skipped`。

这些测试证明 CLI、JSONL 和 Replay 已能共享同一版本化事实格式，序号在恢复后不会倒退，状态筛选和旧入口兼容也没有破坏现有 Agent 行为。
