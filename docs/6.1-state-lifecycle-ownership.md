# 6.1 状态生命周期与所有权模型说明

## 这项工作整体在做什么

6.1 做的事情可以先简单理解为：给 Agent 运行时的各种“状态”登记户口，明确每一类状态是谁的、活多久、存在哪里、谁能改、坏了怎么恢复。

之前项目里已经有很多状态，但它们是散落在不同模块里的：

- `AgentLoop` 里有当前工具循环、Reflection 次数、ProgressSignal、Token 用量；
- `MemoryStore` / `SessionStore` 里有会话历史、session id、episodic / semantic memory；
- `ToolRegistry` 里有工具定义、风险等级、插件来源；
- 后续还会有 Planner、WorkingMemory、PermissionState、FileStateCache、EventBus 等更多状态。

如果不先定义清楚状态边界，后面继续往 AgentLoop 里加字段，很快会变成“谁都能改、谁都不知道该保存到哪、崩了也不知道怎么恢复”的状态泥潭。

所以 6.1 不急着实现完整 `ApplicationState / ConversationState / TurnState / LoopState` 数据类。它先做一件更基础的事：

```text
把状态层级、父子关系、生命周期、所有者、可修改者、持久化边界和恢复策略固定成一张代码里的规格表。
```

一句话总结：

```text
6.1 = 先给未来完整状态系统定“产权和生命周期规则”，6.2 再按这些规则落具体 State 对象。
```

## 1. StateScope 状态范围

对应代码：

- `zzm_agent/core/state_lifecycle.py`
  - `class StateScope`

这个功能做什么：

`StateScope` 定义未来 Conversation Runtime 中正式承认的状态范围：

- `APPLICATION`
- `CONVERSATION`
- `TURN`
- `LOOP`
- `TASK`
- `WORKING_MEMORY`

为什么要这样做：

如果状态名字没有统一定义，后续 6.2、6.3、P4、P7 很容易各写各的，比如有的地方叫 `session_state`，有的地方叫 `conversation`，有的地方直接叫 `memory`。`StateScope` 先把概念统一起来。

## 2. StateLifetime 生命周期

对应代码：

- `zzm_agent/core/state_lifecycle.py`
  - `class StateLifetime`

这个功能做什么：

`StateLifetime` 定义每种状态大概活多久：

- `PROCESS`：进程级，进程退出就结束；
- `SESSION`：会话级，跨多个用户 Turn；
- `USER_TURN`：单次用户输入级；
- `REACT_LOOP`：一次 ReAct 循环内部；
- `LONG_TASK`：长任务级，可跨多个 Turn。

为什么要这样做：

生命周期不同，保存和恢复方式就不同。比如：

- `ApplicationState` 不需要持久化到 session；
- `ConversationState` 需要跨 Turn 恢复；
- `LoopState` 通常只在当前 Turn 内有效；
- `TaskState` 未来需要支持暂停和恢复。

## 3. PersistenceBoundary 持久化边界

对应代码：

- `zzm_agent/core/state_lifecycle.py`
  - `class PersistenceBoundary`

这个功能做什么：

`PersistenceBoundary` 定义状态允许保存在哪里：

- `MEMORY_ONLY`：只在内存中；
- `SESSION_STORE`：保存到会话存储；
- `TASK_STORE`：保存到任务存储；
- `CHECKPOINT_STORE`：保存到检查点。

为什么要这样做：

不是所有状态都应该写入历史文件。比如 Reflection runtime prompt 不应该持久化；但 conversation messages 需要持久化；未来长任务的 WorkingMemory 应该进 task store，而不是污染 semantic memory。

## 4. RecoveryStrategy 恢复策略

对应代码：

- `zzm_agent/core/state_lifecycle.py`
  - `class RecoveryStrategy`

这个功能做什么：

`RecoveryStrategy` 定义状态在中断或重启后怎么处理：

- `RECREATE`：重新创建；
- `RESUME`：恢复继续；
- `ROLLBACK_PENDING`：回滚未提交部分；
- `CHECKPOINT`：从检查点恢复；
- `DISCARD`：丢弃。

为什么要这样做：

Agent 会遇到中断、工具失败、权限拒绝、进程退出。不同状态不能用同一种恢复策略。比如：

- 进程级配置重启后重新创建即可；
- 会话历史应该恢复；
- 当前 Turn 的 pending messages 中断时应该回滚；
- Loop 内部临时状态可以丢弃；
- TaskState 未来要从 checkpoint 恢复。

## 5. StateLifecyclePolicy 状态规则对象

对应代码：

- `zzm_agent/core/state_lifecycle.py`
  - `@dataclass(frozen=True) class StateLifecyclePolicy`

这个功能做什么：

`StateLifecyclePolicy` 是每类状态的完整规则卡片，包含：

- `scope`：状态范围；
- `parent`：父状态；
- `lifetime`：生命周期；
- `owner`：唯一所有者；
- `allowed_writers`：允许修改者；
- `persistence`：持久化边界；
- `recovery`：恢复策略；
- `created_by`：谁创建；
- `destroyed_when`：什么时候销毁；
- `purpose`：状态用途。

为什么要这样做：

后续要实现正式 State 类时，不应该凭感觉写。每个状态都应该先查这张规则卡片，确定它属于谁、谁能改、该不该保存、怎么恢复。

## 6. STATE_LIFECYCLE_POLICIES 规格表

对应代码：

- `zzm_agent/core/state_lifecycle.py`
  - `STATE_LIFECYCLE_POLICIES`

这个功能做什么：

这是一张完整状态生命周期规格表，当前定义：

```text
ApplicationState
└── ConversationState
    ├── TurnState
    │   └── LoopState
    └── TaskState
        └── WorkingMemory
```

### ApplicationState

所有者：

- `ApplicationRuntime`

生命周期：

- 进程级；
- 进程启动时创建；
- 进程退出时销毁；
- 不持久化，重启后重建。

用途：

- 保存配置、模型注册表、工具注册表、Skill 注册表、MCP 连接和当前活动 conversation id。

### ConversationState

所有者：

- `QueryEngine`

生命周期：

- 会话级；
- 打开或创建 session 时创建；
- session 删除或归档时销毁；
- 保存到 session store；
- 重启后可恢复。

用途：

- 保存跨 Turn 的消息、usage、权限、文件缓存、记忆加载状态、当前 Turn 和当前 Task 引用。

### TurnState

所有者：

- `QueryEngine`

生命周期：

- 单次用户输入级；
- 用户提交消息时创建；
- 最终回复、取消、失败或回滚后销毁；
- 通过 checkpoint 保存关键边界；
- 中断后回滚 pending 部分。

用途：

- 保存当前 Turn 的 pending messages、turn usage、发现的 skills、artifacts、permission requests 和 LoopState。

### LoopState

所有者：

- `AgentLoop`

生命周期：

- ReAct loop 内部；
- AgentLoop 执行当前 Turn 时创建；
- Turn 完成、阻塞、取消或失败时销毁；
- 只保存必要 checkpoint；
- 恢复时默认丢弃运行中 loop 状态。

用途：

- 保存 phase、transition、模型/工具迭代次数、tool calls、observations、ProgressSignal 和 Reflection 次数。

### TaskState

所有者：

- `Planner`

生命周期：

- 长任务级；
- Planner 接受长任务目标时创建；
- 任务完成、取消、归档或删除时销毁；
- 保存到 task store；
- 从 checkpoint 恢复。

用途：

- 保存长任务目标、步骤状态、发现、artifacts、blockers 和关联 Turn。

### WorkingMemory

所有者：

- `Planner`

生命周期：

- 跟随 TaskState；
- Task 创建时创建；
- Task 完成、归档或删除时销毁；
- 保存到 task store；
- 从 checkpoint 恢复。

用途：

- 保存任务内临时 notes、confirmed findings、短计划和子步骤摘要，不污染长期记忆。

## 7. 查询函数

对应代码：

- `zzm_agent/core/state_lifecycle.py`
  - `get_state_policy()`
  - `state_lineage()`
  - `state_children()`

这个功能做什么：

这些函数让后续模块不用直接读规格表内部结构。

示例：

```text
state_lineage(StateScope.LOOP)
→ Application → Conversation → Turn → Loop
```

```text
state_children(StateScope.CONVERSATION)
→ Turn, Task
```

为什么要这样做：

6.2 以后实现真实 State 对象时，可以通过这些函数查询父子关系和规则，避免到处硬编码状态层级。

## 8. 规格校验函数

对应代码：

- `zzm_agent/core/state_lifecycle.py`
  - `validate_state_lifecycle_policies()`

这个功能做什么：

校验生命周期规格表是否自洽：

- 每个 `StateScope` 都有 policy；
- policy key 和 policy.scope 一致；
- 状态不能把自己作为父状态；
- owner 不能为空；
- owner 必须在 allowed_writers 中；
- created_by / destroyed_when 不能为空；
- 父状态必须存在；
- 状态层级不能有环。

为什么要这样做：

状态规格是后续 P1 的基础，如果规格表本身错了，后续状态系统会在更隐蔽的地方出问题。先做校验函数和测试，可以让错误尽早暴露。

## 9. 6.1 专项测试

对应代码：

- `tests/test_state_lifecycle.py`

覆盖场景：

- 状态生命周期规格表完整且无校验错误；
- `LoopState` 的 lineage 是 `Application → Conversation → Turn → Loop`；
- `WorkingMemory` 的 lineage 是 `Application → Conversation → Task → WorkingMemory`；
- `ConversationState` 直接拥有 `TurnState` 和 `TaskState`；
- `ApplicationState` 是进程级、内存态、重启重建；
- `ConversationState` 是会话级、session store 持久化、可恢复；
- `TurnState` 和 `LoopState` 的恢复边界不同；
- `TaskState` 和 `WorkingMemory` 是 Planner 拥有的任务级状态。

验证结果：

```text
pytest tests\test_state_lifecycle.py -q -p no:cacheprovider --tb=short
7 passed
```

## 10. 6.1 和 6.2 的边界

6.1 做的是：

- 定义有哪些状态范围；
- 定义父子关系；
- 定义生命周期；
- 定义所有权；
- 定义谁能修改；
- 定义持久化边界；
- 定义恢复策略；
- 用测试固定这些规则。

6.1 不做的是：

- 不实现完整 `ApplicationState` 数据类；
- 不迁移 AgentLoop 字段；
- 不引入正式 QueryEngine；
- 不实现完整状态序列化；
- 不改变 CLI 入口。

这些属于后续任务：

- 6.2：实现 `ApplicationState / ConversationState / TurnState / LoopState`；
- 6.3：实现正式 Loop 状态机；
- 6.17：实现 QueryEngine；
- 6.18：CLI 迁移到 QueryEngine。
