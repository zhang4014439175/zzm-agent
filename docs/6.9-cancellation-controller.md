# 6.9 CancellationController 基础层级模型

这项能力是 zzm-agent 的“停止按钮底座”。用户按下取消、CLI 收到中断、上层任务决定停止，或者未来后台任务超时时，系统需要知道应该停掉哪一层工作、为什么停、什么时候停，以及哪些子工作也必须一起停。`CancellationController` 就是用来统一管理这些取消信号的。

没有这个模型时，取消通常只能靠局部 `KeyboardInterrupt` 或临时布尔值处理：模型调用、工具调用、权限等待、长任务和子任务各停各的，很容易出现“用户已经取消，但工具还在继续跑”“Turn 已经失败，但子任务不知道父任务已停止”“历史里写入了半截结果”这类问题。本任务先把同步链路里的取消状态建成一棵可追踪的树，让后续异步、后台进程和子 Agent 可以复用同一套语义。

本阶段先覆盖 Session、Turn、Task 和 Child Token 的状态表达与同步检查点；异步模型请求、并发工具、后台进程和子 Agent 的完整传播仍留给 P6、P7。

## 功能作用

它主要解决三个问题：

- 让取消有明确边界：取消整个 Session、当前 Turn、某个 Task，还是某个工具子操作；
- 让取消可以向下传播：父任务取消后，子工具、子任务和后续新建的子 Token 都能继承取消状态；
- 让执行链路能在安全检查点停下：停止前回滚 pending message，标记运行状态，并保留取消原因。

取消树由 `CancellationController` 统一创建和持有：

```text
Session Token
├── Turn Token
├── Task Token
└── Child Tokens
```

每个 `CancellationToken` 支持：

- `reason`：取消原因；
- `cancelled_at`：取消时间；
- `children`：子 Token；
- `register_callback()`：取消时触发一次回调；
- `raise_if_cancelled()`：在同步检查点抛出 `CancellationError`；
- `to_record()` / `from_record()`：保存和恢复取消树状态。

父 Token 取消会递归传播给所有子 Token。父 Token 已取消后创建的新子 Token 会立即继承取消状态。

## 使用场景举例

### 例子 1：用户在工具执行前取消当前 Turn

用户让 Agent 修改文件，模型已经决定调用 `write_file`，但在工具真正执行前用户按下取消。同步链路会先检查当前 Task Token：

```text
Turn Token: turn-123
└── Task Token: task-turn-123-agent-loop
    └── Tool Token: tool-call-write-file
```

如果 Session 或 Turn 已经被取消，Tool Token 会继承 `reason="user_interrupt"`，`AgentLoop` 不再调用工具，而是：

- 回滚本轮尚未提交的 assistant/tool message；
- 将 `TurnState.status` 标记为 `cancelled`；
- 将 `LoopState.phase` 标记为 `cancelled`；
- 保留取消原因，便于 CLI 或后续 EventBus 展示。

这样可以避免“用户以为取消了，但文件还是被写了”的问题。

### 例子 2：长任务的父级取消传播给子步骤

未来 Planner 执行一个长任务时，可能会拆成多个子步骤：读文件、跑测试、生成补丁。如果用户取消整个任务，只需要取消父 Task Token，下面的子 Token 都会自动变成 cancelled：

```text
Task Token: task-refactor
├── Child Token: tool-read-file
├── Child Token: tool-run-tests
└── Child Token: tool-apply-patch
```

子步骤在自己的检查点调用 `raise_if_cancelled()`，就能得到同一个取消原因和时间，不需要每个模块各自发明取消协议。

### 例子 3：Session 已取消后禁止新 Turn 继续运行

如果上层运行时已经取消整个 Session，再启动新的 Turn 时，新建的 Turn Token 会立即继承 Session Token 的取消状态。`AgentLoop` 在模型调用前检查到取消，不会再请求模型，也不会写入半截历史。

## 代码位置

- `zzm_agent.core.runtime_state.CancellationToken`
- `zzm_agent.core.runtime_state.CancellationController`
- `zzm_agent.core.runtime_state.CancellationError`
- `zzm_agent.core.runtime_state.ConversationState.cancellation`
- `zzm_agent.core.agent_loop.AgentLoop`

`ConversationState` 会在创建时初始化 session 级 `CancellationController`，每次 `start_turn()` 会创建并绑定 turn token。`AgentLoop` 可接收外部 `CancellationController`，也会在没有外部 controller 时为当前 store session 创建默认 controller。

## 同步执行链路

`AgentLoop.run()` 当前接入以下同步检查点：

- turn 启动时创建 Turn Token 和 Task Token；
- 模型调用前检查 Task Token；
- 每轮工具调用前检查 Task Token；
- 每个工具执行前创建 Tool Child Token；
- 工具 retry 执行和 retry sleep 前后检查 Tool Child Token；
- 流式中断会取消 Turn Token，并保持原有不写入部分 assistant/tool 状态的历史安全语义；
- 外部取消会回滚 pending message，标记 `TurnState` / `LoopState` 为 cancelled，并保存当轮 usage。

本阶段不会强制终止已经进入阻塞中的同步函数调用；它提供的是同步检查点模型。未来后台进程、并发工具和异步模型流会在此基础上注册更强的取消回调。
