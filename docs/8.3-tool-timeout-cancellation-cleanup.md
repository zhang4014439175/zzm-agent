# 8.3 工具超时、取消与资源清理

## 一句话说明

这项功能负责在 Agent 调用工具时处理三件事：执行时间过长、用户要求取消，以及工具结束后的资源清理。

开发前，这些保护分散在不同位置，有些工具甚至完全没有。开发后，所有通过工具注册中心运行的工具都会走同一个检查和清理入口。这样可以避免已经取消的任务继续启动工具，也能让超时和清理失败以明确错误显示出来。

## 为什么需要它

Agent 不只是生成文字，还会调用搜索、文件、Shell 和插件等工具。这些工具可能运行很久，也可能在运行过程中打开文件、创建临时目录、建立连接或持有锁。

以前主要有以下问题：

- 用户已经取消任务，但某些直接调用工具注册中心的路径仍可能启动工具；
- 普通工具没有统一的最长执行时间设置；
- 工具失败后，临时资源是否释放完全依赖工具自己处理；
- 工具运行过久时，系统可能只返回普通失败，用户不知道是不是超时；
- Shell、插件和普通 Python 工具各自处理这些问题，容易出现遗漏。

8.3 把这些共同规则放进工具的统一执行入口。只要工具从这个入口执行，就会接受相同的取消检查、超时判断和结束清理。

## 一个实际使用例子

假设用户让 Agent 搜索一个很大的项目，搜索工具最长允许执行 2 秒。

1. Agent 准备启动搜索工具。
2. 系统先检查用户是否已经取消任务。如果已经取消，搜索不会启动。
3. 如果没有取消，搜索开始运行，同时系统记录开始时间。
4. 搜索过程中创建了临时文件，因此工具提前登记了“结束后删除临时文件”的清理动作。
5. 搜索实际运行了 3 秒才返回，超过了允许的 2 秒。
6. 系统在工具返回后确认已经超时，不再把搜索结果当成正常结果交给 Agent。
7. 系统执行之前登记的清理动作，释放临时资源。
8. 用户会收到明确的超时错误，而不是一个含糊的“工具执行失败”。

这个例子有一个重要限制：普通同步 Python 函数一旦开始运行，目前不能在第 2 秒到来时立刻从中间强行切断。强行切断可能让文件只写了一半，或者让锁和连接来不及释放。因此系统会等函数运行到可以安全检查的位置，再报告超时并停止后续处理。

如果运行的是 Shell 子进程，现有 Shell 工具可以使用子进程超时机制真正终止命令。两者的停止方式不同，但最终都会明确报告超时。

## 开发前和开发后的区别

| 情况 | 开发前 | 开发后 |
| --- | --- | --- |
| 工具启动前用户取消 | 主要依赖 AgentLoop 检查，直接调用注册中心的路径可能遗漏 | 工具注册中心会再次检查，已经取消时不启动工具 |
| 单个工具运行太久 | 普通工具没有统一时间设置 | 工具可以声明自己的最长执行时间 |
| 普通同步工具超过时间 | 可能被当作普通失败或继续返回结果 | 在下一处安全位置报告明确的超时错误 |
| 工具结束后的资源释放 | 每个工具自行处理，容易遗漏 | 可以统一登记清理动作，成功、失败、取消或超时都会执行 |
| 多个清理动作 | 没有统一顺序 | 最后登记的资源最先释放，避免先释放仍被其他资源依赖的对象 |
| 清理本身失败 | 可能静默丢失 | 主任务成功时会明确报告清理失败 |

“安全位置”指不会把工具停在写了一半或状态不完整的位置，例如工具启动前、工具返回后，以及自动重试之前。

## 现在已经支持的能力

- 每个工具可以单独设置最长执行时间；
- 用户取消状态会从当前任务传递到具体工具；
- 工具启动前会检查取消，避免已经取消后仍产生新的操作；
- 工具返回后会再次检查取消和用时，阻止过期结果继续进入后续流程；
- 工具可以登记一个或多个清理动作；
- 无论工具成功、失败、取消还是超时，系统都会尝试执行清理动作；
- 多个清理动作按照“后登记、先执行”的顺序运行；
- 超时和清理失败会转换成明确、可记录的工具错误；
- 旧插件或测试替身即使暂时不接受新的取消参数，仍会在调用前后接受取消检查。

## 当前限制（还做不到什么）

- 不能立刻强制停止正在运行的普通同步 Python 函数，只能在下一处安全位置发现取消或超时；
- 如果工具内部存在长时间循环，它仍应主动定期检查取消状态，才能更快停止；
- 需要立即终止的长任务，应使用可终止的子进程、异步工具或后续的后台任务管理器；
- 本阶段没有实现完整的 MCP 客户端和后台进程管理，只为它们规定了以后需要接入的执行规则；
- 如果工具失败，同时清理动作也失败，系统优先保留工具原本的失败原因，避免真正的问题被清理错误覆盖；
- 文件修改记录和 `/undo` 撤销功能不属于本任务，将在 8.4 实现。

## 给开发者看的实现位置

- `zzm_agent/core/tool_registry.py`
  - `tool(..., timeout_seconds=...)`：登记工具时保存该工具允许执行的最长时间；
  - `ToolRegistry.call()`：统一执行参数校验、取消检查、用时判断和资源清理；
  - `register_cleanup()`：为某个工具登记结束后必须执行的清理动作；
  - `ToolDeadlineExceeded`：表示工具已经超过规定时间；
  - `ToolCleanupError`：表示工具主体成功，但结束清理失败。
- `zzm_agent/core/agent_loop.py`
  - 把当前工具对应的取消状态传给工具注册中心；
  - 对旧式注册器做能力检查，避免新增参数破坏已有插件和测试替身。
- `zzm_agent/core/runtime_state.py`
  - 提供分层取消控制，让会话、当前轮次和具体工具之间可以传递取消状态。
- `zzm_agent/core/errors.py`
  - 把工具超时转换成不可自动重试的结构化错误，并给出下一步处理建议。
- `zzm_agent/plugins/shell.py`
  - Shell 子进程继续使用可真正终止命令的超时处理。

简化后的执行顺序如下：

```text
准备调用工具
  -> 检查是否已经取消
  -> 执行工具
  -> 再次检查是否取消
  -> 检查是否超过允许时间
  -> 无论前面结果如何都执行清理
  -> 返回正常结果，或报告取消、超时、清理失败
```

## 测试如何证明它有效

- `tests/test_tool_registry.py` 验证已经取消时工具不会启动、工具超时会被识别、清理动作一定执行，而且多个清理动作顺序正确；
- `tests/test_agent_loop.py` 和 `tests/test_runtime_state.py` 验证取消状态能从 Agent 运行过程传到具体工具；
- `tests/test_tool_error_recovery.py` 验证超时会显示成明确错误，并且系统不会盲目重复执行已经超时的工具；
- Replay 和 Eval 测试验证新增调用参数没有破坏旧的工具注册器和既有任务回放。

专项回归结果为 `98 passed`，说明与工具执行、取消、错误恢复和旧注册器兼容有关的测试全部通过。

全量回归结果为 `327 passed, 2 skipped`，说明本次修改没有破坏项目中其他已经覆盖的功能。两个跳过项是测试套件原本按环境条件跳过的用例，不是本次失败。
