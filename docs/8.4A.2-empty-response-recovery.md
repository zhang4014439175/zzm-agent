# 8.4A.2 空模型回复与异常完成恢复

## 一句话说明

模型同时没有返回文字和工具调用时，系统不再把它当成任务完成。系统会在同一任务中有限次数地要求模型继续；仍然为空时，会明确阻塞并告诉用户恢复次数、执行进度和模型结束标记。

## 为什么需要它

旧逻辑只对“已经调用过工具后的第一次空回复”重试一次。第二次仍为空，或者第一次模型调用就为空时，空字符串会进入正常完成分支。终端于是没有最终消息，直接回到输入框，看起来像程序无故停止。

空回复只说明这次模型响应没有可用动作，不能证明用户要求已经完成。必须先恢复，恢复失败后也必须明确告知用户。

## 一个实际使用例子

用户输入“检查项目并完成剩余模块”。Agent 已经执行若干工具，模型服务随后返回空内容，结束标记为 `stop`。系统插入一条只在本轮生效的恢复要求，让模型继续工具执行、给出有效答复或说明阻塞。

如果下一次模型给出总结，任务正常完成。如果配置允许恢复两次，而三次响应都为空，终端会显示任务因 `empty_model_response` 阻塞，并列出模型调用次数、工具轮次、上下文估算、模型结束标记以及“可输入继续”的入口。历史中不会写入空的最终答复。

## 功能的大致流程

1. 系统收到一次模型响应，并检查是否有可见文字或工具调用。
2. 只要其中一项存在，就继续原有流程：执行工具或处理最终答复。
3. 两项都不存在时，系统记录本次模型结束标记，但拒绝把任务标记为完成。
4. 如果尚未达到 `empty_final_retries`，系统加入恢复要求并再次调用模型。恢复要求不会写入长期对话历史。
5. 后续响应恢复正常时，系统继续同一个任务，不产生额外的用户轮次。
6. 达到恢复次数后仍为空，系统结束为阻塞，提交一条可见说明，并保存恢复次数和结束原因。
7. 用户可以根据提示输入“继续”重新发起后续请求；任务不会静默回到提示符。

## 开发前和开发后的区别

开发前：首次响应为空会直接完成；工具执行后的第二次空回复也会直接完成；模型服务的结束标记被丢弃。

开发后：任何“无文字且无工具”的响应都进入同一恢复规则。恢复次数可配置，失败后状态为阻塞，终端与快照都能解释原因。

## 现在已经支持的能力

- 工具调用前和工具调用后的空回复使用相同判定。
- 默认自动恢复两次，可通过 `agent.empty_final_retries` 调整，允许设为 `0` 以直接阻塞。
- 恢复提示要求模型继续任务、调用必要工具、给出最终答复或明确阻塞。
- 记录非流式和流式模型响应的结束标记。
- 恢复耗尽后显示模型调用次数、工具轮次、上下文估算和继续方式。
- 空回复不会作为空 assistant 消息提交，也不会把本轮标记为完成。

## 当前限制（还做不到什么）

- 当前恢复只处理“完全没有文字且没有工具调用”。内容被截断但仍有文字时，尚未自动判断任务是否完整。
- 恢复会继续使用当前上下文；8.5 完成前还没有为超长工具结果自动生成轻量引用。
- 输入“继续”目前会创建新的用户轮次；同一任务的无感自动续段由 8.4A.4 实现。

## 给开发者看的实现位置

- `zzm_agent/core/agent_loop.py`：识别空响应、插入恢复提示、计算次数并在耗尽后阻塞。
- `zzm_agent/core/model_adapter.py`：从模型服务响应和流式分片提取结束标记。
- `zzm_agent/cli_support/runtime.py`：读取 `agent.empty_final_retries`，默认值为 2，并传给循环。
- `config.yaml`：展示空回复恢复次数的配置示例。
- `zzm_agent/core/query_engine.py`：把阻塞结果作为事件发出并以 `turn.blocked` 保存快照。

## 测试如何证明它有效

测试分别模拟首次模型调用为空、工具调用后为空、有限恢复后成功、恢复耗尽、模型结束标记为 `stop`、阻塞事件和快照持久化。针对相关核心模块与 CLI 的回归测试结果为 `164 passed`，完整测试为 `336 passed, 2 skipped`。这说明空回复不会再静默完成，同时正常响应和现有工具流程保持可用。
