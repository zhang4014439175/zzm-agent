# 8.4A.1 统一终止原因与结束可观测性

## 一句话说明

现在每次任务把控制权交回终端时，都会明确说明任务是完成、暂时让出、阻塞、失败还是取消，并记录具体原因。以前有些路径只返回一段文字甚至空字符串，用户无法判断为什么停下；现在终端、事件和会话快照使用同一份结束记录。

## 为什么需要它

Agent 停止输出不一定代表任务完成。它可能是用户取消、权限阻塞、模型异常、内部安全限制，未来也可能只是长任务换一个执行段。如果这些情况都表现为“回到输入框”，用户就会误以为任务已经做完，排查时也没有证据。

本功能把“模型为什么结束一次回复”和“整个用户任务为什么结束”分开。Provider finish reason（模型服务给出的单次回复结束标记）会被保存，但它不能单独证明任务已完成。

## 一个实际使用例子

用户要求 Agent 检查项目并修改多个文件。模型调用工具后连续返回空内容，最终没有形成答复。系统把本轮标记为 `blocked`，原因是 `empty_model_response`，同时保留模型服务返回的 `stop`。

终端不再直接出现新提示符，而会显示类似 `Ended: blocked (empty_model_response, provider=stop)` 的结束说明。会话快照中也保存相同状态。之后查看记录时，可以确认这是空回复阻塞，不是任务正常完成。

## 功能的大致流程

1. 用户提交请求后，系统建立本轮运行状态。
2. 每次模型回复时，系统单独记录模型服务给出的结束标记。
3. Agent 根据实际执行结果判断任务状态。有效最终答复是完成；安全让出是暂时让出；无法继续是阻塞；异常是失败；用户中断是取消。
4. 状态确定后，系统生成一份结束记录，包含状态、原因、模型结束标记、恢复次数和发生时间。
5. 结束记录随会话状态写入快照，并通过统一事件发送给终端或其他调用方。
6. 终端明确显示结束状态和原因。正常答复仍会照常显示；异常路径不再只靠空字符串或普通文本暗示结果。

## 开发前和开发后的区别

开发前：正常结束、阻塞和取消分别修改不同字段，没有统一的结束记录；会话快照总是写成 `turn.completed`；终端的富文本模式会忽略状态事件。

开发后：五种结束状态使用统一记录。快照原因会随实际结果写成 `turn.completed`、`turn.blocked`、`turn.failed` 等。终端会显示结束原因，JSON 事件也能读取相同信息。

## 现在已经支持的能力

- 区分 `completed`、`yielded`、`blocked`、`failed` 和 `cancelled`。
- 持久化任务状态、结束原因、发生时间、恢复次数和模型结束标记。
- 保存每次模型调用的结束标记历史。
- 在普通文本终端、富文本终端和结构化事件中输出结束记录。
- 按真实状态填写会话快照的保存原因。
- 为后续“长任务安全让出并自动续段”预留正式的 `yielded` 状态。

## 当前限制（还做不到什么）

- `yielded` 目前只有状态协议，尚未用于工具轮次上限；该行为由 8.4A.3 实现。
- 当前结束判断仍以本轮是否得到有效文本或明确阻塞为主，尚未根据任务计划逐项检查完成证据。
- 计划级完成门禁将在后续 TaskRunner 和 CompletionGate 中实现。

## 给开发者看的实现位置

- `zzm_agent/core/runtime_state.py`：定义五种状态、统一结束记录及其序列化。
- `zzm_agent/core/model_adapter.py`：保留非流式与流式响应的模型结束标记。
- `zzm_agent/core/query_engine.py`：按真实状态保存快照，并发出统一结束事件。
- `zzm_agent/core/model_stream.py`：定义可供 CLI 和其他客户端消费的结束事件。
- `zzm_agent/cli_support/rendering.py`：在普通文本与富文本终端显示状态、原因和模型结束标记。

## 测试如何证明它有效

自动化测试覆盖结束记录的序列化恢复、模型结束标记归一化、QueryEngine 事件和快照原因，以及终端展示。针对 AgentLoop、运行状态、流式查询和 CLI 的回归测试共 `164 passed`；完整测试为 `336 passed, 2 skipped`。这证明旧的正常回复、工具调用和命令行为没有因统一结束协议而失效。
