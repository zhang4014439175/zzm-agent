# 9.2 Skills 模块化与发现状态

## 一句话说明

以前 `/skills` 只能提示“尚未接入”，项目也不能把一套可复用的任务做法交给智能体。现在可以把做法写成一个本地 Skill，也就是“按需加载的任务说明包”。用户明确点名它，或当前请求命中它的触发短语后，系统才会加载正文和参考资料，并记录为什么启用、读了哪些文件、占用了多少上下文空间。

## 为什么需要它

项目指令文件适合放所有任务都要遵守的规则。如果把代码审查、发布检查、故障排查等每套长流程也全部塞进项目指令，每一次简单问答都要携带无关内容。上下文会更拥挤，模型也更容易混用不相关步骤。

Skill 把这些专门做法拆成独立目录。系统启动或执行 `/skills` 时只查看每个包开头的名称、说明和触发条件；真正需要时才读取完整步骤。这样既能复用流程，又不会让所有请求持续承担同样的内容成本。

## 一个实际使用例子

项目作者在 `.zzm_agent/skills/python-review/SKILL.md` 中写入：

```markdown
---
name: python-review
description: 审查 Python 改动并给出按严重程度排序的问题
triggers: [审查 Python]
resources: [references/checklist.md]
allowed_tools: [read_file, search]
scripts: [scripts/check_types.py]
---
先阅读改动及相关测试。只报告能够从代码中定位的问题，并说明触发条件。
```

用户输入“请使用 `$python-review` 审查这次修改”。系统先从名称识别出这是显式启用，然后读取 `SKILL.md` 正文；如果资源预算仍有剩余，再读取包内的 `references/checklist.md`。这些内容作为当前执行的专门说明交给模型，但不会被写进会话历史，也不会自动运行 `scripts/check_types.py`。

用户随后执行 `/skills`，可以看到 `python-review` 是否可用，以及最近一次任务激活了哪些 Skill、加载了多少资源、估算消耗了多少 Token。Token 是模型处理文字时使用的计量单位，这里用来限制说明包占用的上下文空间。

## 功能的大致流程

1. 启动时从配置的本地目录建立 Skill 管理器。目录不存在不会导致启动失败。
2. 每次准备模型上下文时，系统扫描这些目录的直接子目录。发现阶段只读取 `SKILL.md` 开头的元数据，不读取正文和资源。
3. 系统依次检查三种激活来源：用户使用 `$名称` 或 `@skill:名称` 明确点名；配置把 Skill 固定启用；用户请求包含 Skill 声明的触发短语。
4. 命中的 Skill 先经过禁用策略。配置禁用优先于包内设置；被拒绝时记录原因，不加载内容。
5. 通过检查后，系统才读取正文和声明资源。资源必须位于该 Skill 自己的目录内；越界、缺失、无法读取或超出预算都会被跳过并留下原因。
6. 加载内容进入当前模型请求。系统提前从可用历史空间中扣除它的成本，避免专门说明挤掉用户当前请求。
7. 本轮的可用项、候选项、已激活项、固定项、拒绝原因、资源和成本进入状态快照。任务恢复后仍可解释这次选择。
8. `/skills` 只刷新轻量目录并展示状态，不会因为用户查看列表就加载正文或执行脚本。

如果一个 Skill 格式损坏，系统只隔离该包并继续发现其他包。若同名包出现在多个目录，按配置目录顺序保留第一个，避免同一名称在一次任务中得到两套相互冲突的说明。

## 开发前和开发后的区别

开发前：

- `/skills` 只有占位提示。
- 专门工作流只能长期放在系统提示或项目指令中，每轮都占空间。
- 无法解释某个工作流为何出现，也没有资源成本和拒绝原因记录。
- Skill 目录里的参考文件没有统一的路径和预算保护。

开发后：

- 本地 `SKILL.md` 可被显式名称、固定配置或触发短语激活。
- 未命中的 Skill 只读取少量元数据，正文与资源按需加载。
- 配置可以禁用或固定启用指定 Skill。
- 包外路径、缺失资源和预算耗尽均会被安全跳过并记录原因。
- 当前任务和恢复快照能说明发现、激活、资源及成本。
- `/skills` 能列出可用和禁用状态，并展示最近一次加载结果。

## 现在已经支持的能力

- 每个 Skill 使用独立目录和一个 `SKILL.md` 入口。
- YAML 头部支持 `name`、`description`、`triggers`、`enabled`、`resources`、`allowed_tools` 和 `scripts`。
- 支持 `$python-review` 与 `@skill:python-review` 两种显式点名方式。
- 支持触发短语匹配，以及 `skills.pinned` 固定启用。
- 支持 `skills.disabled` 集中禁用，包内也可设置 `enabled: false`。
- 支持正文总预算和资源总预算；超限内容会截断或拒绝。
- 资源只能来自自身目录，符号链接解析后越界同样拒绝。
- 支持保存完整发现状态，并在 `/skills` 中查看最近一次激活结果。

## 当前限制（还做不到什么）

- 现在只发现配置目录的直接子目录，不递归搜索任意深度。
- 触发短语使用大小写不敏感的文本包含匹配，不做语义相似度判断。
- `allowed_tools` 当前是给模型看的工作流声明，不会授予权限，也不会自动隐藏其他工具。工具定义按需暴露属于 9.3。
- `scripts` 只记录可选脚本名称，不会自动执行。脚本若由后续工具调用执行，仍必须经过现有权限、沙箱和审计入口。
- `/skills` 是只读状态展示，不提供安装、卸载或在线市场。插件分发属于后续 9.4。
- 本阶段不支持从网络下载 Skill，也不信任包外资源。

## 给开发者看的实现位置

- `zzm_agent/skills/manager.py`
  - `SkillDefinition` 保存发现阶段的轻量元数据。
  - `SkillDiscoveryState` 保存 available、discovered、activated、pinned、rejected、加载资源、成本和激活原因。
  - `SkillManager.discover()` 只读取 YAML 头部并隔离坏包或同名包。
  - `SkillManager.build_messages()` 选择当前任务候选，执行禁用检查并渐进加载正文。
  - `SkillManager._load_resources()` 限制资源目录和预算，不执行声明脚本。
- `zzm_agent/core/context_preparation.py`
  - `ContextPreparationService.prepare()` 在会话历史组装前计算 Skill 成本，在当前用户消息前插入专门说明，并把来源加入上下文诊断。
- `zzm_agent/core/agent_loop.py`
  - `AgentLoop.__init__()` 接收可选 Skill 管理器。
  - `AgentLoop._run_turn()` 把本轮发现状态复制到 Turn，供快照、恢复和上层查询。
- `zzm_agent/core/state/turn.py`
  - `TurnState.to_record()` 与 `from_record()` 持久化完整 Skill 状态，同时保留旧的名称集合兼容字段。
- `zzm_agent/cli_support/bootstrap.py`
  - `build_runtime()` 解析 Skill 目录、禁用项、固定项和预算，并把同一个管理器交给执行链路和 CLI。
- `zzm_agent/cli_support/commands/router.py`
  - `_handle_skills()` 只刷新元数据并展示目录与最近状态。
- `config.yaml`
  - `skills.directories`、`disabled`、`pinned`、`max_skill_tokens` 和 `max_resource_tokens` 提供默认策略。

执行链路是：CLI 装配本地目录 → 上下文准备按用户输入发现候选 → Skill 管理器校验与加载 → 当前模型请求获得专门说明 → AgentLoop 写入 Turn 状态 → QueryEngine 持久化快照或 `/skills` 展示状态。

## 测试如何证明它有效

`tests/test_skills.py` 覆盖以下行为：

- 发现时只读取元数据，显式点名后才加载正文。
- 触发短语、固定启用和配置禁用的优先级正确。
- 包外资源被拒绝，资源预算耗尽后不会继续读取。
- Skill 内容只进入当前模型上下文，并进入预算来源记录。
- 完整发现状态经过 Turn 序列化后可以恢复。
- `/skills` 能列出元数据且不会因查看命令加载正文。

实际执行结果：

- 受影响模块定向回归：`181 passed`。
- 全量回归：`400 passed, 2 skipped`。
- Python 编译检查：`python -B -m compileall -q zzm_agent tests` 通过。

这些结果证明显式和隐式触发、渐进加载、禁用、预算、目录隔离、上下文注入、状态恢复和 CLI 展示形成了一个可运行闭环，同时没有破坏现有 AgentLoop、CLI、状态序列化和其他回放测试。
