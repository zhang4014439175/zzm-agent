# 8.4A.3 SegmentResult 与安全让出

## 一句话说明

工具轮次或上下文达到单段边界时，Agent 不再把整个任务判为失败或完成，而是生成 `yielded` 检查点。检查点记录本段原因、轮次、工具调用、Artifact、上下文和剩余工作，让上层可以安全继续。

## 为什么需要它

`max_tool_iterations` 的本意是限制一次连续执行占用的资源，不应该代表用户任务已经结束。旧实现达到上限就返回阻塞消息，大任务即使仍在正常推进也会停止。

安全让出把“单段结束”和“任务结束”分开。重复循环、权限问题、失败和取消仍保留原来的安全边界，不会因为支持续段而失效。

## 一个实际使用例子

用户要求检查二十个模块，配置每段最多执行五轮工具。第五轮完成后，系统提交已有工具调用和结果，生成一个检查点，并将该段标记为 `yielded`。

检查点包含工具轮次、工具调用总数、相关 Artifact、上下文预算和“继续检查剩余模块”的摘要。它不是最终答复，也不会显示成任务失败；QueryEngine 可以据此开始下一段。

## 功能的大致流程

1. Agent 在一个执行段内正常调用模型和工具。
2. 每轮结束后更新工具轮次、调用次数、观察结果和上下文额度。
3. 达到工具轮次上限，或当前段上下文已无法安全容纳下一次调用时，系统选择安全边界。
4. 当前段的用户消息、工具意图和工具结果先提交到历史，避免续段时丢失证据。
5. 系统生成检查点，记录原因、原任务、轮次、Artifact、上下文和剩余工作摘要。
6. Turn 状态改为 `yielded`，检查点随状态快照持久化。
7. 同步 `run()` 仍返回字符串；需要结构化信息的调用方使用 `run_segment()` 获取 `SegmentResult`。

## 开发前和开发后的区别

开发前：达到 `max_tool_iterations` 后直接 `blocked/iteration_limit`，用户必须缩小任务或手动继续。

开发后：该配置表示单段边界，结果为 `yielded/segment_tool_iteration_limit`。上下文边界使用 `yielded/segment_context_budget`，任务级决定交给 QueryEngine。

## 现在已经支持的能力

- `SegmentResult` 包含状态、原因、回复、工具轮次、工具调用数、检查点、剩余工作摘要和 Turn。
- 工具轮次上限与上下文边界都能安全让出。
- 检查点持久化到 Turn 状态和会话快照。
- 同步 `run()` 保持字符串返回兼容。
- 重复调用、无进展、连续失败、权限阻塞和取消仍按原安全规则处理。

## 当前限制（还做不到什么）

- 检查点的剩余工作摘要目前由运行时生成，不是基于正式计划步骤计算。
- 进程完全退出后的跨进程自动续跑尚未实现；当前检查点可以恢复和解释，但自动续段发生在同一次 QueryEngine 请求内。
- 完整的任务计划与证据门禁属于后续 10.2A。

## 给开发者看的实现位置

- `zzm_agent/core/segments.py`：定义 `SegmentResult` 结构与序列化记录。
- `zzm_agent/core/agent_loop.py`：检测边界、提交段内消息、生成检查点并返回结构化结果。
- `zzm_agent/core/runtime_state.py`：定义 `yielded` 状态和检查点持久化字段。
- `tests/test_agent_loop.py`、`tests/test_agent_replay.py`：验证同步兼容和轮次边界行为。

## 测试如何证明它有效

测试确认达到单段上限只调用配置数量的工具，结果状态为 `yielded`，检查点包含轮次、调用数、来源和剩余工作；反思不会重置边界，Replay 也使用相同协议。完整回归结果为 `348 passed, 2 skipped`。
