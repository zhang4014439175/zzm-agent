# 8.8 RuntimeState 拆分

## 一句话说明

以前应用、会话、单轮对话、工具循环、权限和取消状态都集中在一个接近两千行的文件中，很难看出每类状态由谁负责。本次把它们按生命周期拆到独立模块，同时保留原导入路径。用户恢复会话、取消任务或批准工具时不会看到用法变化，但状态问题更容易定位，后续功能也不必继续挤进同一个文件。

## 为什么需要它

运行状态决定了 Agent 当前在哪个会话、哪一轮、是否等待权限、是否已经取消，以及进程重启后能恢复哪些内容。这些状态的生命周期不同：应用状态跟随进程，会话状态可以跨多轮保存，单轮状态只属于一次用户输入，工具循环又只是单轮内部的一部分。

开发前，这些定义和辅助函数集中在 `runtime_state.py`。代码虽然能运行，但模块边界没有表达所有权。修改权限恢复时可能误碰循环状态，增加取消字段时也需要在一个超大文件中定位。

本次只移动定义和调整内部导入，不改变状态含义、保存格式或用户操作。

## 一个实际使用例子

用户在会话 `project-a` 中输入：“运行测试，如果失败就告诉我原因。”

1. 应用状态找到或创建 `project-a` 会话，并把它设为当前会话。
2. 会话状态创建一轮新的对话状态，记录用户输入、用量、权限和取消令牌。
3. 单轮状态启动工具循环。循环状态从准备阶段进入模型调用，再进入工具校验和执行阶段。
4. 如果测试命令需要确认，权限状态记录请求以及用户的批准或拒绝。
5. 如果用户按下取消，取消控制器把取消信号从会话或单轮传播到当前任务和工具。
6. 执行结束后，单轮状态记录完成、阻塞、失败或取消原因。会话快照按原有 JSON 字段保存。
7. 程序重启后，系统从快照恢复 `project-a`。恢复出的会话、单轮、循环、权限和取消对象来自拆分后的模块，但用户看到的历史和状态与拆分前一致。

## 功能的大致流程

1. 程序启动时创建应用级状态，用来管理配置、共享资源和会话集合。
2. 用户选择会话时，应用状态返回对应的会话级状态。
3. 用户提交消息后，会话状态创建单轮状态，并建立该轮的取消令牌。
4. 单轮状态创建工具循环状态，记录模型调用、工具执行、反思和终止阶段。
5. 工具需要授权时，权限状态保存请求、决定和作用范围。
6. 用户取消时，取消状态沿父子关系传播，执行点检查到信号后停止。
7. 状态保存时，各模块仍输出原来的记录字段；恢复时按同样的嵌套关系重建。
8. 旧代码如果仍从 `core.runtime_state` 导入，会由兼容门面获得新模块中的同一个类，不会产生两套不兼容状态。
9. 记录损坏、非法循环转换或重叠 Turn 等错误仍沿用原来的明确失败行为。

## 开发前和开发后的区别

开发前：

- 六类核心状态和 File/Memory 辅助状态都定义在 `runtime_state.py`。
- 文件超过 1900 行，模块位置无法直接表达状态所有权。
- 核心代码普遍依赖这个集中模块。

开发后：

- Application、Conversation、Turn、Loop、Permission、Cancellation 各自拥有独立模块。
- FileStateCache 和 MemoryLoadState 放入独立 support 模块，不再夹在六类核心状态之间。
- 核心运行代码直接从新状态包或具体子模块导入。
- `runtime_state.py` 只保留兼容导出，不再保存实际定义。
- 旧入口与新入口返回同一个类对象，序列化恢复不会混入包装子类。

## 现在已经支持的能力

- 从新状态包统一导入全部运行状态。
- 按具体生命周期模块直接导入单类状态。
- 继续使用全部旧 `core.runtime_state` 导入名称。
- 保持应用、会话、Turn 和 Loop 的所有权关系。
- 保持权限请求、一次性/会话/任务授权及恢复行为。
- 保持会话、Turn、Task 和子操作的取消传播。
- 保持状态快照、校验、迁移和恢复字段不变。
- 保持 FileStateCache 与 MemoryLoadState 的原有功能。

## 当前限制（还做不到什么）

- 本任务只拆分模块，没有改变状态机规则，也没有新增任务规划状态。
- 状态对象仍主要是进程内 Python 对象；持久化继续使用现有快照方案。
- FileStateCache 和 MemoryLoadState 暂时共用 `state/support.py`，尚未各自建立更细目录。
- 本任务没有实现跨进程并发状态写入、数据库事务或远程状态服务。
- WorkspaceRuntime 属于 8.9，统一 RuntimeEvent 与 ExecutionJournal 属于 8.10。

## 给开发者看的实现位置

- `zzm_agent/core/state/application.py`：定义进程级 `ApplicationState`。
- `zzm_agent/core/state/conversation.py`：定义跨 Turn 的 `ConversationState`。
- `zzm_agent/core/state/turn.py`：定义 `TurnState`、`TurnStatus` 和 `TurnTermination`。
- `zzm_agent/core/state/loop.py`：定义 `LoopState`、阶段、转换原因和非法转换检查。
- `zzm_agent/core/state/permission.py`：定义权限请求、决定、授权作用域和恢复逻辑。
- `zzm_agent/core/state/cancellation.py`：定义层级取消令牌、异常和控制器。
- `zzm_agent/core/state/support.py`：保存文件读取缓存和 Memory 加载辅助状态。
- `zzm_agent/core/state/__init__.py`：提供新状态包统一导出。
- `zzm_agent/core/runtime_state.py`：为旧调用方提供对象身份一致的兼容导出。

执行链路：

```text
ApplicationState 管理会话
→ ConversationState 创建 Turn
→ TurnState 创建 Loop 和取消令牌
→ LoopState 记录模型与工具阶段
→ PermissionState 记录工具授权
→ CancellationController 传播取消
→ 各状态按原 Schema 保存和恢复
```

## 测试如何证明它有效

`tests/test_state_module_compatibility.py` 验证：

- 旧兼容门面导出的类与新模块定义是同一个对象。
- 六类核心状态的实际归属模块已经改变，不是简单增加别名文件。
- 应用、会话、Turn 和 Loop 嵌套状态经过旧入口序列化再恢复后，类型和记录完全一致。

`tests/test_runtime_state.py`、`tests/test_state_lifecycle.py` 和 `tests/test_state_serialization.py` 继续覆盖状态转换、所有权、权限、取消、快照、迁移和恢复。`tests/test_agent_replay.py` 验证运行回放没有变化。

实际验证结果：

- 状态、生命周期、序列化与 Replay 定向回归：`54 passed`。
- 完整回归：`367 passed, 2 skipped`。

这些测试证明状态定义已经真正移动，同时旧导入、嵌套类型、持久化格式和运行语义保持兼容。
