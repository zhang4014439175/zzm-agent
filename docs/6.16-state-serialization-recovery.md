# 6.16 状态序列化、版本迁移与恢复协议

6.16 解决的是“运行时状态能不能放心落盘、升级后还能不能读、重启后该恢复到哪里”的问题。前面的 PermissionState、FileStateCache、MemoryLoadState、CancellationController、EventBus、ArtifactStore 和 CheckpointStore 已经能记录事实，但它们还缺一个统一外壳：文件里是什么版本、有没有被写坏、旧格式怎么迁移、恢复前要检查哪些外部条件。

典型场景是：用户让 Agent 运行测试，过程中产生权限决策、文件读取缓存、记忆注入记录、工具日志 Artifact 和取消 token。程序崩溃或用户重启后，系统不应该盲目继续执行一个已经停在模型调用或工具执行中的 Turn；它要先读取快照，校验 checksum、工作区、文件版本和 Artifact，再判断这个快照是可以恢复、需要阻塞等待用户处理，还是已经失败。

## 代码位置

- `zzm_agent/core/runtime_state.py`
  - 为 `LoopState`、`TurnState`、`ConversationState`、`ApplicationState` 增加 `to_record()` / `from_record()`。
  - 顶层状态会把 Usage、权限、文件缓存、记忆加载、取消 token、事件、Artifact、Checkpoint 和 active turn 一起转成 JSON 友好的 dict。
- `zzm_agent/core/state_serialization.py`
  - `StateEnvelope`：状态快照外壳，包含 `schema_version`、`state_type`、`payload`、`metadata`、`checksum`。
  - `migrate_state_record()`：把旧记录或旧 schema 迁移到当前版本。
  - `StateSnapshotStore`：复用 `StorageIO` 做原子写入、备份和损坏 JSON 隔离。
  - `RecoveryValidator`：把恢复结果分成 `recoverable`、`blocked`、`failed`。
- `tests/test_state_serialization.py`
  - 覆盖 envelope、迁移、checksum、快照读写、损坏文件隔离和恢复判定。

## 使用示例

保存一个会话状态：

```python
conversation = ConversationState(session_id="session-a")
turn = conversation.start_turn("run tests", turn_id="turn-1")
turn.start_loop().record_model_call()

store = StateSnapshotStore(".zzm/sessions/session-a/state.json")
store.save(conversation, state_type="conversation")
```

恢复时读取并还原：

```python
store = StateSnapshotStore(".zzm/sessions/session-a/state.json")
conversation = store.load_state(ConversationState.from_record)
```

真正继续执行前，还要做恢复判定：

```python
envelope = store.load_envelope()
decision = RecoveryValidator().validate(
    envelope,
    context=RecoveryValidationContext(
        workspace_path=".",
        artifact_paths=[record["path"] for record in envelope.payload["artifacts"]],
        has_checkpoint=True,
    ),
)
```

如果 `decision.status == recoverable`，上层 QueryEngine 才能继续或展示可恢复状态；如果是 `blocked`，应该向用户说明原因，例如 Artifact 丢失、记忆文件版本变化、运行中 Turn 没有 checkpoint；如果是 `failed`，说明快照本身或工作区条件已经不可信。

## 执行链路

```text
运行时状态对象
  -> to_record()
  -> StateEnvelope(schema_version + checksum)
  -> StateSnapshotStore.save()
  -> StorageIO.write_json()
  -> 原子替换 + .bak 备份

重启恢复
  -> StateSnapshotStore.load_envelope()
  -> StorageIO.read_json()
  -> 损坏 JSON 隔离 / 备份恢复
  -> migrate_state_record()
  -> checksum 校验
  -> RecoveryValidator.validate()
  -> from_record() 还原状态对象
```

这条链路把“能读出来”和“能继续运行”分开：读出来只代表快照格式可信；能继续运行还要通过恢复判定。

## 恢复规则

- 已完成、已阻塞、已取消、已失败的 Turn 可以作为历史状态恢复。
- `pending` / `in_progress` 的 Turn 必须有可用 checkpoint；否则恢复结果是 `blocked`。
- 如果运行中 Turn 停在 `calling_model`、`streaming_response`、`validating_tool_calls`、`awaiting_permission` 或 `executing_tools` 等中间阶段，默认也会阻塞，避免重复模型请求或重复执行工具。
- Artifact 路径缺失时阻塞，因为 UI 和回放无法打开完整日志或结果。
- 记忆文件版本和当前版本不一致时阻塞，避免用已经变化的 Memory 上下文伪装成旧 Turn。
- 工作区路径不存在时失败，因为恢复环境已经不成立。
- checksum 不匹配时抛出 `StateSerializationError`，代表快照被篡改或写坏。

## 当前边界

- 6.16 只提供协议和基础验证，不负责把 CLI 主入口迁移到 QueryEngine；这留给 6.17-6.18。
- 恢复判定当前是保守策略：不确定能否安全重放的运行中状态会阻塞，而不是自动继续。
- `CheckpointStore` 仍保留原有接口；通用状态快照通过 `StateSnapshotStore` 复用 `StorageIO` 的写入和损坏隔离能力。
