# 5.4 回放基准扩充说明

本文档记录 5.4「回放基准扩充」做了什么，并明确每个功能点对应到哪里的代码。5.4 的目标是把 5.2 Reflection 和 5.3 工具错误恢复的关键行为固化为 deterministic replay benchmark，避免这些安全机制以后被改坏却没有被发现。

## 执行链路总览

5.4 的核心链路是：

```text
zzm_agent/eval/benchmarks/*.yaml
→ run_eval(suite="replay")
→ _run_replay(case, workspace)
→ ReplayLLM 按 YAML 回放模型输出
→ MockToolRegistry 按 YAML 返回工具结果或抛异常
→ AgentLoop.run()
→ _check_extended_replay_expectations(...)
→ 检查调用次数、Reflection、ProgressSignal、工具结果 JSON 和重试等待
```

对应代码：

- `zzm_agent/eval/runner.py`
  - `_ReplayMemoryStore`
  - `_run_replay()`
  - `_exception_from_mock()`
  - `_check_extended_replay_expectations()`
  - `_requests_contain_text()`
  - `_history_has_tool_json()`
- `zzm_agent/eval/benchmarks/07_reflection_repeated_observation.yaml`
- `zzm_agent/eval/benchmarks/08_error_category_recovery.yaml`
- `zzm_agent/eval/benchmarks/09_retry_after_external_service.yaml`
- `tests/test_eval_runner.py`

## 1. Replay 专用内存 Store

对应代码：

- `zzm_agent/eval/runner.py`
  - `class _ReplayMemoryStore`

这个功能做什么：

`_ReplayMemoryStore` 是 replay eval 专用的内存版 Store，提供 AgentLoop 需要的最小接口：

- `load_history()`
- `build_turn_messages()`
- `append()`
- `save_latest_context()`

为什么要这样做：

Replay suite 的目标是验证 AgentLoop 的确定性行为，不是测试 MemoryStore 的磁盘读写。当前 Windows 环境下部分临时目录存在权限问题，如果 replay eval 依赖真实文件 Store，容易被环境问题干扰。内存 Store 让 replay 基准专注于模型回放、工具调用和安全机制。

代码上怎么串起来：

```text
_run_replay()
→ loop = AgentLoop(..., store=_ReplayMemoryStore(), ...)
→ AgentLoop.run()
→ 历史消息写入内存 history
→ 后续 expected 可以检查 tool result JSON
```

## 2. Replay Runner 扩展断言

对应代码：

- `zzm_agent/eval/runner.py`
  - `_check_extended_replay_expectations()`

这个功能做什么：

5.4 之前，replay benchmark 主要只能检查：

- 是否调用过某个工具；
- 是否禁止调用某个工具；
- 最终输出是否包含某段文本。

5.4 增加了更细的断言能力：

- `model_call_count`：模型调用次数；
- `reflection_count`：Reflection 触发次数；
- `progress_reason`：最后一次 ProgressSignal 原因；
- `tool_call_count`：工具调用总次数；
- `tool_call_sequence`：完整工具调用顺序和参数；
- `runtime_prompt_contains`：运行时模型请求中是否出现指定提示；
- `retry_delays`：自动重试等待时间；
- `tool_result_json_contains`：工具 Observation JSON 是否包含指定字段。

为什么要这样做：

只检查最终输出不够。比如模型最后说“完成”，但中间可能没有触发 Reflection，或者错误分类 JSON 已经退化。扩展断言能检查 AgentLoop 的关键中间状态，让 replay benchmark 真正具备防回归价值。

## 3. YAML 异常模拟

对应代码：

- `zzm_agent/eval/runner.py`
  - `_exception_from_mock()`
- `zzm_agent/eval/benchmarks/08_error_category_recovery.yaml`
- `zzm_agent/eval/benchmarks/09_retry_after_external_service.yaml`

这个功能做什么：

benchmark YAML 现在可以通过 `exception` 字段声明工具要抛出的异常。

支持示例：

```yaml
mock_tool_results:
  - name: "read_file"
    arguments:
      path: "missing.py"
    exception: "FileNotFoundError"
    message: "missing.py"
```

支持的异常类型：

- `FileNotFoundError`
- `PermissionError`
- `TimeoutError`
- `ConnectionError`
- `TypeError`
- 其他名称默认转为 `RuntimeError`

为什么要这样做：

5.3 的错误分类逻辑发生在 `tool_error_from_exception()` 中。如果 YAML 只返回已经构造好的 `ToolError`，就绕过了真实异常转换链路。通过 YAML 声明异常，可以让 replay benchmark 覆盖真实的错误分类路径。

## 4. Retry-After 回放验证

对应代码：

- `zzm_agent/eval/runner.py`
  - `_exception_from_mock()`
  - `_run_replay()`
  - `_check_extended_replay_expectations()`
- `zzm_agent/eval/benchmarks/09_retry_after_external_service.yaml`

这个功能做什么：

`09_retry_after_external_service.yaml` 模拟远程服务限流：

```yaml
exception: "ConnectionError"
retry_after_seconds: 2.0
```

Runner 会把它变成带 `retry_after_seconds` 属性的 `ConnectionError`。AgentLoop 捕获后会：

```text
ConnectionError
→ tool_error_from_exception()
→ ToolError(category="external_service", retry_after_seconds=2.0)
→ _retry_delay_for_error()
→ retry_sleep(2.0)
```

测试中 `retry_sleep` 被设置为 `retry_delays.append`，所以不会真的等待，只记录等待值。

对应 YAML 断言：

```yaml
expected:
  retry_delays:
    - 2.0
  tool_result_json_contains:
    - error_type: "ConnectionError"
      category: "external_service"
      deterministic: false
      retryable: true
      attempts: 2
      retry_after_seconds: 2.0
```

为什么要这样做：

这把 5.3 的 Retry-After 行为从单元测试提升到了 replay benchmark。以后如果重试策略被改坏，replay suite 可以直接发现。

## 5. Reflection 重复 Observation 基准

对应代码：

- `zzm_agent/eval/benchmarks/07_reflection_repeated_observation.yaml`
- `zzm_agent/eval/runner.py`
  - `runtime_prompt_contains`
  - `reflection_count`
  - `progress_reason`

这个功能做什么：

该基准模拟模型连续读取不同文件，但工具结果都一样：

```text
read_file("a.py") → "no target here"
read_file("b.py") → "no target here"
read_file("c.py") → "no target here"
```

ProgressMonitor 应检测到：

```text
progress_reason = "repeated_observation"
```

AgentLoop 应注入一次：

```text
[REFLECTION_REQUIRED]
```

对应 YAML 断言：

```yaml
expected:
  model_call_count: 4
  reflection_count: 1
  progress_reason: "repeated_observation"
  runtime_prompt_contains:
    - "REFLECTION_REQUIRED"
    - "repeated_observation"
```

为什么要这样做：

这个基准把 5.1 的无进展检测和 5.2 的 Reflection 串起来验证。它不只检查最终回答，还检查中间是否真的触发了纠偏提示。

## 6. 错误分类恢复基准

对应代码：

- `zzm_agent/eval/benchmarks/08_error_category_recovery.yaml`
- `zzm_agent/eval/runner.py`
  - `_history_has_tool_json()`
  - `tool_result_json_contains`

这个功能做什么：

该基准模拟读取不存在文件后，模型改用搜索工具：

```text
read_file("missing.py") → FileNotFoundError
grep_search("target") → "src/real.py:10: target"
```

对应 YAML 断言：

```yaml
expected:
  tool_result_json_contains:
    - error_type: "FileNotFoundError"
      category: "environment"
      deterministic: true
      retryable: false
      attempts: 1
```

为什么要这样做：

它验证 5.3 的错误分类结果真的出现在模型可见的 tool Observation 中，而不是只存在于内部对象里。

## 7. 工具调用序列断言

对应代码：

- `zzm_agent/eval/runner.py`
  - `_check_extended_replay_expectations()`
  - `tool_call_sequence`

这个功能做什么：

YAML 可以要求工具调用必须严格等于某个序列，包括参数。

示例：

```yaml
tool_call_sequence:
  - name: "read_file"
    arguments:
      path: "missing.py"
  - name: "grep_search"
    arguments:
      pattern: "target"
```

为什么要这样做：

只检查工具名是否出现过不够精确。Agent 可能调用了正确工具但参数错了，或者顺序错了。严格序列断言可以让 replay benchmark 更可靠。

## 8. Runtime Prompt 断言

对应代码：

- `zzm_agent/eval/runner.py`
  - `_requests_contain_text()`

这个功能做什么：

Runner 可以检查模型请求中的运行时消息是否包含指定文本。

当前用于验证：

- `REFLECTION_REQUIRED`
- `repeated_observation`

为什么要这样做：

Reflection Prompt 是 runtime-only，不会写入持久历史。如果只检查历史，是看不到它的。因此必须检查 `ReplayLLM.requests` 中实际发给模型的 messages。

## 9. Tool Result JSON 断言

对应代码：

- `zzm_agent/eval/runner.py`
  - `_history_has_tool_json()`

这个功能做什么：

Runner 会遍历历史中的 `role: "tool"` 消息，尝试解析 JSON，并检查是否包含指定字段。

当前用于验证：

- FileNotFoundError 被分类为 `environment`；
- ConnectionError 被分类为 `external_service`；
- Retry-After 和 attempts 被写入模型可见 Observation。

为什么要这样做：

Agent 框架里“给模型看的 Observation”比内部变量更重要。这个断言确保模型真的能看到结构化错误恢复信息。

## 10. 5.4 专项测试

对应代码：

- `tests/test_eval_runner.py`
  - `test_replay_benchmark_checks_reflection_expectations()`
  - `test_replay_benchmark_checks_tool_error_category_expectations()`
  - `test_replay_benchmark_checks_retry_after_expectations()`
  - `test_replay_benchmark_fails_when_expected_reflection_is_missing()`

这个功能做什么：

这些测试直接加载新增 benchmark YAML，并调用 `_run_replay()` 验证：

- Reflection 基准能通过；
- 错误分类基准能通过；
- Retry-After 基准能通过；
- 当期望值故意写错时，runner 会返回失败。

为什么要这样做：

不仅要测试 AgentLoop，也要测试 benchmark runner 本身能发现失败。否则 YAML 写了很多 expected，但 runner 实际不检查，就会形成“假基准”。
